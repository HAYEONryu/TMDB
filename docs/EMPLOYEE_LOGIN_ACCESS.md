# 직원 로그인과 현장·고객 조회

2026-11-11 KST. 직원 계정의 반복 비밀번호 변경 화면과 오늘 할 일의 현장 선택·고객 미표시 신고를 점검했다. 실제 서버 접속·배포·사용자 계정/DB 변경은 하지 않았다.

## 비밀번호 변경

현재 코드의 비밀번호 변경은 비밀번호·변경필수 해제·세션 버전 증가를 같은 트랜잭션으로 저장한다. 가상 직원의 최초 변경 → 로그아웃 → 두 번째·세 번째 로그인은 정상이고 변경필수 상태가 다시 켜지지 않았다. **실제 서버에서 반복되는 원인은 미확정**이다. 서버의 계정 상태·실행 이미지·접속 경로와 관리자 재설정 여부를 확인해야 하며 전체 계정의 플래그를 임의로 해제하지 않는다.

변경 완료 계정이 예전 `/auth/password` 주소로 접속하면 업무 화면으로 돌아가도록 보완했다. 직접 비밀번호를 변경하려면 상단 계정 설정의 **비밀번호 변경**을 선택한다(`/auth/password?change=1`). 이때는 변경필수 안내 대신 자발적 변경임을 표시하고 업무 화면 복귀 링크를 제공한다. 신규 계정과 관리자 재설정 후에는 계속 필수 변경을 요구하며 현재 비밀번호·새 비밀번호 검증도 유지한다.

실제 서버에서 재발하면 로그인한 브라우저의 개발자 도구 콘솔에서 아래를 실행해 **status·role·must_change_password 세 값과 현재 주소의 경로만** 확인한다. 비밀번호·쿠키·API 키·전화번호·전체 `/api/me` 응답을 공유하지 않는다.

```js
fetch('/api/me', {cache: 'no-store'}).then(async response => {
  const data = await response.json();
  console.log({status: response.status, role: data.role,
    must_change_password: data.must_change_password});
});
```

변경한 비밀번호로 로그인했는데 `must_change_password: true`이면 실제 계정 상태와 변경/재설정 작업 순서를 확인해야 한다. false이면 예전 주소·설정 메뉴·오래된 화면과 실행 중인 코드 버전을 확인한다. 401이면 세션이 종료된 상태다. 재현되지 않았다는 이유만으로 운영 서버 원인이 해결됐다고 판정하지 않는다.

## 오늘 할 일·나의 DB

기존에는 공개 HTTP 주소에서 Web Crypto·Web Locks를 사용할 수 없으면 현장 선택·고객 조회까지 모두 중단했다. 이 경로가 현장 비활성화/고객 미표시 증상과 일치한다. 이제 사전 저장 지원 검사에서 제한을 발견하면 **조회 전용**으로 전환한다.

- 현장 선택·검색·정렬·페이지 이동과 본인 현재 담당 고객/상담·재콜 이력 조회는 가능하다.
- 고객 표를 표시한 다음 레이아웃을 계산해 처음 열린 HTTP 표의 셀 위치를 정상화한다.
- 상담 편집·저장·재콜 완료·삭제 요청·AI 생성은 중단한다. 암호화 키/context를 요청하거나 암호화/다중 탭 보호를 우회하지 않으며 평문 대기열도 만들지 않는다.
- 계정/세션 검증이 실패하거나 계정이 비활성화되면 고객 표를 숨긴다. 계정 전환 후 늦게 도착한 이전 인증 응답이 표를 다시 열지 않도록 차단한다. 직원에게 관리자 비고를 제공하지 않는 서버 권한은 유지한다.
- 실제 브라우저 보관소 열기 자체가 실패한 경우에는 기존 복구 안내·차단을 유지한다. 저장 지원이 정상인 HTTPS/localhost 환경에서는 기존 편집·자동 저장·재시도·충돌 처리 흐름을 사용한다.

**오늘 할 일**은 선택 현장의 본인 현재 담당 고객 중 오늘 할당 또는 오늘/지난 재콜 대상이다. 과거에 할당됐고 재콜 대상도 아니면 **나의 DB**에서 확인한다. 전체 현장이나 다른 직원의 고객을 합쳐 표시하지 않는다. HTTP 조회 가능은 직원 상담 업무 전체가 준비됐다는 뜻이 아니며 공개 직원 편집·저장에는 HTTPS 준비가 계속 필요하다.

분리된 PostgreSQL 17·가상 사용자/고객과 실제 Chromium에서 변경 범위 **56개 검사(백엔드 28·브라우저 28)**에 통과 근거가 있다. HTTP 레이아웃 보완 후 해당 브라우저 8개를 재실행했고, 마지막 계정 전환 보호 후 관련 3개를 검증했다. 모두 한 실행에서 통과했다고 표시하지 않는다.

각 실행 중 소스 변경 없음도 확인했다. 실패 기록을 덮어쓰지 않고 `.local/verification-runs/<실행ID>/`에 보존한다. 실제 고객정보·외부 AI 호출·개발/데모 DB 변경은 없으며 AI 활성화/무료 확인 설정도 바꾸지 않았다. 운영 서버의 현재 비밀번호 상태·실행 이미지·HTTPS와 실제 반영은 미검증이다.

```sh
.venv/bin/python scripts/run_final_verification.py start
.venv/bin/python scripts/run_final_verification.py test --label employee-access-recovery \
  tests.test_auth tests.browser_flow \
  tests.browser_http_environment.EmployeeEnvironmentBrowserTests \
  tests.browser_employee tests.browser_ui
.venv/bin/python scripts/run_final_verification.py stop
```

## 서버 반영

추가 migration이나 계정/DB 초기화는 필요 없다. 사용자 서버는 기존 두 Compose 파일과 비밀 설정을 유지한 채 최신 코드를 받아 웹·스케줄러 이미지를 재빌드·재시작한다. [Docker 서버 반영 절차](CUSTOMER_GRID_EDITING.md#기존-docker-서버-반영)를 따른다. 브라우저를 새로고침하고 새 비밀번호 재로그인, 오늘 할 일·나의 DB의 현장 선택, HTTPS 환경의 실제 저장을 각각 확인한다. AI 작업자는 이 변경을 위해 시작하지 않는다.
