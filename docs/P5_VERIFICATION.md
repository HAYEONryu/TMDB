# P5 직원 화면·자동 저장 검증

2026-11-04, Asia/Seoul. v2.0·개발 계획의 P5만 구현했다. P6은 시작하지 않았다. 설계서 원문과 기존 사용자 데이터·변경을 보존했다. 실제 개인정보·유료 API·유료 자원·운영 배포는 사용하지 않았다.

## 1. 구현 결과

| 기능 | 결과 |
|---|---|
| 직원 오늘 할 일/나의 DB | 본인의 현재 담당·선택 현장·삭제 제외, KST 오늘 할당 OR 오늘/과거 미완료 재콜, 중복0, 재콜 우선 정렬 |
| 편집/조회 | 상담6필드 편집, 담당/이름/연락처/할당일 읽기 전용, 서버 검색·열별 후보/날짜/비고 필터·50/100행 페이지 |
| 자동 저장 | 첫 유효 변경 후90초 목표, 추가 입력으로 연장0, 변경/원복 coalesce, 최대100행/배치 |
| 지속 대기열 | 사용자/현장/고객/할당/lane별 IndexedDB, AES-GCM 암호화·계정별 runtime 키·식별자 인증 |
| 전송 중 새 입력 | 고정 inflight와 이후 pending 분리, ACK 후 이후 입력 보존·기준 버전 갱신 |
| 복구/충돌 | 동일 계정 로그인 후 현재 권한/할당/삭제/버전·receipt 확인, 서버/내 값 비교·명시적 재적용/폐기 |
| 오류/이동 | 저장 중/오프라인/재시도/충돌/전송 불가/입력 오류 구분, 실패 중 메뉴/로그아웃 재시도·취소·폐기 확인 |
| 격리 | 계정 헤더·쓰기 잠금 내 직원 역할 재확인, 다른 계정의 기록 조회/전송0, 인증 실패 자동 재시도 중단 |
| 다중 탭 | entry 소유 잠금·고객 send 잠금, 뒤의 서버 버전 충돌을 조용히 덮어쓰지 않음 |
| 직원 복사 제한 | 표의 copy/cut/contextmenu·Ctrl/Cmd C/X 차단, 붙여넣기 허용, 선택 체크박스·내보내기 없음 |

기존 고객/재콜/최초 진행/revision/receipt의 행 단위 원자성을 재사용했다. 조회·무변경·저장 전 원복은 진행이 아니며, 실제 저장만 진행과 revision을 만든다. 이전 할당 ID를 새 ID로 바꿔 전송하지 않는다.

## 2. 실제 실행한 검증

```sh
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py migrate --noinput
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/python manage.py test tests tests.browser_flow tests.browser_p2 tests.browser_imports tests.browser_p4 tests.browser_employee tests.performance_imports tests.performance_assignments --noinput -v 2
node --experimental-default-type=module --test tests/employee_queue.test.mjs
```

**총206개 통과: Django195개 + Node11개.** Django는 서버173개·Chromium20흐름·1만 행 성능2개이며 설계서의 인수 항목 수와는 별개다. 기존 P1~P4의170개도 다시 실행했다. 최종 Django195개는74.943초, Node11개는0.12초에 통과했다. 실제 기본 PBKDF2 브라우저 로그인과 별도 PostgreSQL `test_tm_dev`를 사용했으며 테스트 DB는 종료 시 삭제했다. Node는 네트워크/보관 어댑터를 주입해 결정적인 상태 경합을 검증하며 실제 브라우저 검증을 대체하지 않는다.

| 저장 시계 | 변경 없는95초간 저장0, 입력60초 뒤 재입력해도 최초100초 이내 전송, 최신값만 저장, 추가 무변경100초간 추가 저장0 |

원시 로그는 `.local/p5-tests-complete.log`, `.local/p5-queue.log`, 시계 증거는 `.local/p5-timing.json`이다. 시계 테스트의 최종 확인 시점은 최초 입력 직후 측정 기준 **92.435초**(실행별 조금 변함)이며 그 전에 저장 요청이 시작되고 ACK를 확인했다. 브라우저 시계를 조정한 검증이며 실제 경과90초를 기다리는 부하 시험은 아니다.

기존 성능 회귀도 통과했다. 실제 PG 1만 행 업로드는 검증2.313초/등록3.241초/합계5.554초·RSS126.17MiB·최대 업무 잠금3.225초였다.1만 건 랜덤 분배/회수는3.785초/4.987초/합계8.771초·RSS141.48MiB·최대 잠금4.979초였다. 공통 기준30초/RSS512MiB/잠금10초 이내다. `.local/p3-performance.json`, `.local/p4-performance.json`은 현재 회귀 실행 결과로 갱신되었고 이전 측정 원시 로그·문서는 유지했다.

Gunicorn2 workers와 실제 로컬 PG로 `/healthz`200, 직원 API 익명401, 최종 JS4개·CSS의 HTTP 바이트 SHA/Content-Length 일치를 확인했다(`.local/p5-runtime.json`). `check` 이상0, 모델 변경/미적용 migration0. 기존 개발 DB 사용자3명·고객65건·현재 할당0건을 유지했다. 가짜 기존 계정의 비밀번호는 변경하지 않았다.

## 3. 실패 이력과 수정

초기 브라우저 검증에서 존재하지 않는 cell 메서드 사용, 아직 생성되지 않은 cell 참조, 입력 중 row 재생성으로 편집기가 닫히는 문제가 발견되어 수정했다. 상태 갱신은 활성 편집기를 보존한다. 테스트의 브라우저 재로그인은 쿠키만 비우고 IndexedDB를 보존하도록 고쳤고, 강제 저장이 후속 입력까지 이미 저장한 뒤 비활성 버튼을 누르던 테스트를 ACK 기준으로 바로잡았다. Quota 주입 함수의 반환 평가와 원복 helper의 잘못된 대기 기대도 고쳤다.

첫 전체 회귀의 실패1개는 P2 테스트가 과거 본인 할당의 재분배를 여전히 FORBIDDEN으로 기대한 것이다. v2.0의 지정 오류인 ASSIGNMENT_CHANGED/409와 서버 정보 비노출을 검사하도록 갱신했다. 권한 거부는 유지하고 관계없는 고객은 계속 FORBIDDEN이다. 이후 전체194개 통과, 입력 오류 상태 문구와 브라우저 회귀를 추가한 최종195개 통과를 확인했다. 중간 로그 `.local/p5-first.log`·`p5-browser-*.log`·`p5-focused*.log`·`p5-tests.log`·`p5-tests-final.log`도 보존했다. 의도적500/503 오류 경로 로그를 테스트 실패로 집계하지 않았다.

## 4. 사용자 확정사항과 구현 기본값

| 구분 | 적용 |
|---|---|
| 확정 규칙 | 고객명/연락처 수정 금지·현재 담당/할당만 저장·100초 이내 전송 시작·복사 제한·상담 보존·진행 기준 유지 |
| 설계서 기본값 |90초 목표·최대100행·receipt7일·2/5/15/30/60초 재시도·KST 표시 |
| P5 구현 기본값 | AES-256-GCM/HMAC·runtime non-extractable 키·IndexedDB strict durability·문서 lane UUID·Web Locks·10초 fetch timeout·90~100% jitter·1초 활성 tick |

설계서 원문/업무 규칙은 변경하지 않았다. 암호화·문서별 lane은 계정 격리와 다중 탭 복구를 구체화한 구현이다.100초는 정상 온라인/활성 화면에서 전송 시작 기준이며 서버 장애·탭 정지에서 성공을 보장하지 않는다.

## 5. 직접 확인과 남은 범위

실행·가짜 계정·분배·오프라인·두 탭 충돌 확인은 [README13](../README.md#13-p5-직원-화면자동-저장-확인)을 따른다. 화면 증거는 `.local/qa/p5-employee-desktop.png`, `.local/qa/p5-employee-mobile.png`이며 직접 열어 검토했다.

P6의 재콜 완료/취소·상담 이력 조회·대시보드 상세 집계·23시/누락 자동 회수는 미구현이다. P7 삭제 요청/관리자 승인·영구 삭제, P8 이후 화면 통합, P9~P12 AI와 운영 보안, P13 백업/복원·종합 인수도 남았다. 이미 있는 일정 저장·삭제 요청 모델·일반 휴지통 이동/복구는 유지했다. 전체92개 인수 완료를 주장하지 않는다.

Docker 엔진이 없어 이미지 build/up·레이어 검사는 미실행이다. 실제 검증 브라우저는 Chromium이며 Safari/Firefox·실제 모바일 기기·전원 차단 복구·운영 HTTPS/복원·SECRET_KEY 교체는 검증하지 않았다. 브라우저 프로세스 재시작은 확인했으나, 저장소 자체가 삭제되거나 아직 transaction을 완료하지 못한 입력까지 복구하는 것은 아니다. 운영 배포와 유료 호출은 실행하지 않았다. 작업에서 시작한 Gunicorn/전용 PostgreSQL을 정상 종료했고8000 포트 비점유·DB 중지 상태를 확인했다. 다시 실행하는 명령은 README1에 있다.
