# 분리형 데모 · 10분 따라하기

화면 브랜드는 **두드림 TM**이다. 현재는 PC 왼쪽 네이비 메뉴와 블루 강조, 모바일 상단 메뉴로 통일했다. 팀장 대시보드에서 상담결과 기간과 직원별 분배/영업 진행을 선택할 수 있다. 저장/분배/승인 버튼과 업무 규칙은 유지한다. [최신 화면·집계 기준](BLUE_DASHBOARD.md)을 참고한다.

AI 키를 보존한 상태에서 향후 유료 기능을 켜거나 다시 끄는 명령은 [AI 활성화 안내](AI_ACTIVATION.md)를 따른다. 현재는 opt-in 표시도 없고 AI worker도 실행하지 않는다.

2026-11-07, Asia/Seoul. **현재 데모 웹과 PostgreSQL을 실행 상태로 유지했다.** 모든 계정·고객·엑셀 내용은 가짜다. 실제 AI 생성은 비활성이고 AI worker·자동 회수 scheduler는 실행하지 않는다. 데모 도중 날짜가 바뀌거나 23시가 지나도 자동 회수로 자료가 달라지지 않는다.

관리자 Safari 창과 직원 가 Chrome 창을 로그인 상태로 열어 두었다. 서로 다른 브라우저를 사용하면 세션이 섞이지 않는다. 같은 Chrome 프로필의 일반 창 두 개는 세션을 공유하므로 서로 다른 계정의 창으로 사용하지 않는다. Chrome 게스트 창을 닫으면 다시 로그인하면 되며 서버에 저장한 자료는 유지된다. 브라우저의 암호 저장은 선택하지 않았다.

이 데모 계정은 별도 DB에 처음 만들 때부터 위 비밀번호로 준비했으므로 바로 업무 화면에 들어간다. 기존 개발 계정·비밀번호나 실제 앱의 초기 비밀번호 변경 규칙을 바꾸지 않았다. 이후 사용자가 데모 비밀번호를 바꾸면 재시작 시 덮어쓰지 않는다.

## 10분 순서

이미 검증한 `검증완료 데모현장`에는 결과가 남아 있다. 처음부터 따라 하려면 **새 현장**을 만든다. 예: `직접체험-1107-0130`처럼 겹치지 않는 이름. 다른 화면으로 이동할 때는 현장 선택이 새 현장인지 확인한다. 새 현장이 기존 전역 기본 현장을 자동으로 바꾸지는 않는다.

| 시간 | 창 | 버튼 순서와 확인할 결과 |
|---|---|---|
| 0–1분 | 관리자 Safari·직원 Chrome | 위 계정으로 각각 로그인. 이미 로그인돼 있으면 상단 이름으로 역할 확인 |
| 1–3분 | 관리자 | **DB 관리 → 현장 생성 → 현장명 → 생성 → 엑셀 업로드**. 업로드 화면에서 새 현장 선택 → 첫 파일 선택 → **파일 검증**. `등록 가능4 / 파일 내 중복1 / 형식 오류1` 확인 → **업로드 확정 → 등록 확정**. 이어 **다른 파일 검증**으로 두 번째 파일 선택 → **파일 검증**, `기존 중복1` 확인. 두 번째 파일은 확정하지 않고 다음 단계로 이동 |
| 3–4분 | 관리자 | **DB 분배·회수 → 새 현장 선택 → 확인**. 직원 `데모직원가`, 직원당 수량 `2` → **분배**. 선택을 `데모직원나`, 수량 `1`로 바꾸고 **분배**. 총4건 중 직원 가2·직원 나1·미할당1 |
| 4–6분 | 직원 가 | **나의 DB → 새 현장 선택**. 배정된 두 고객 중 한 고객을 기억한다. **상담기타내용(비고) 셀 더블클릭 → 가짜 상담 입력 → 제목 클릭**. **재콜일정 셀 더블클릭 → 미래 날짜·오전/오후·시·분을 모두 입력 → Enter → 지금 저장**. `모든 변경 저장됨` 확인. 90초 자동 저장을 기다릴 필요 없음 |
| 6–7분 | 직원 가 | 같은 행의 오른쪽 **삭제 요청 → 확인**. `요청완료` 확인. 이 단계에서는 고객이 아직 행에 남아 있음. 체크박스 일괄 요청은 없음 |
| 7–8분 | 관리자 | **대시보드 → 삭제 요청 새로고침 → 해당 고객 승인 → 확인 → 휴지통 → 새 현장 선택**. 기존 비고 아래에 `[한국 시각] 고객요청으로 인한 삭제`가 추가됐는지 확인. 재콜일정도 남고 담당은 해제됨. **영구 삭제는 누르지 않음** |
| 8–10분 | 두 창 | 휴지통 새로고침 후 같은 비고·재콜 유지 확인. 직원 가의 **나의 DB → 새로 확인**에서 승인된 고객이 빠졌는지 확인. 추가로 직원 가 로그아웃 → 직원 나 로그인 → 같은 현장 **나의 DB**에서 자기1건만 보이고, 직원 가 고객명 검색 시0건인지 확인. 끝나면 직원 가로 다시 로그인 가능 |

재콜·작업 열이 안 보이면 **표 안을 가로로 스크롤**한다. 날짜를 키보드로 입력할 때는 연/월/일과 오전·오후/시/분을 모두 채운다. `2026-11-08 오후 03:00`은 이번 확인에 쓴 예이며, 체험 시에는 원하는 미래 시각으로 입력하면 된다. 날짜 셀의 방향키와 Tab은 날짜 입력기가 처리하도록 수정했다.

| AI | 기존 설정 보존 | 빈 키·비활성 설정, 실제 `.env.ai` 대신 데모 전용 경로 |

기존 개발 PostgreSQL은 계속 중지 상태이며 접속·초기화·migration·seed를 하지 않았다. 데모를 만들기 전과 비교해 기존 클러스터의 `pg_control`·`PG_VERSION` 해시가 동일하고 PID 파일도 없다. 그 안의 고객 데이터를 읽거나 변경하지 않았다. 실제 `.env`·`.env.ai` 파일을 수정하지 않았다.

데모는 영속 PostgreSQL이다. 브라우저 창을 닫거나 아래 stop/start를 실행해도 저장한 값은 남는다. 시작 명령은 기존 데모 계정·비밀번호·고객을 덮어쓰거나 초기화하지 않는다. 데모 폴더와 제어 스크립트는 `.local` 아래 Git 제외 자료이므로 이 컴퓨터에 보존한다.

## 종료·재실행

터미널에서 프로젝트 폴더로 이동한 뒤 실행한다. 종료는 데모 웹과 데모 DB만 정상 종료한다. 폴더 삭제나 DB 초기화 명령은 포함하지 않는다.

```sh
cd /Users/hayeon/Documents/TMDB

# 상태
.venv/bin/python .local/demo/site.py status

# 종료 — 자료 보존
.venv/bin/python .local/demo/site.py stop

# 다시 실행 — 기존 데모 자료 그대로
.venv/bin/python .local/demo/site.py start

# 한 번에 종료 후 재실행
.venv/bin/python .local/demo/site.py restart
```

다시 실행한 뒤 같은 `http://localhost:8010/auth/login`을 연다. 포트 충돌 시 다른 프로세스를 임의로 종료하지 말고 `.local/demo/web.log`·`postgres.log`를 확인한다. 이 데모는 이 컴퓨터의 localhost용이며 다른 기기에 공개하거나 운영 배포하지 않았다.

## 수정과 검증 근거

재콜 날짜의 방향키/Tab이 Tabulator의 행·셀 이동으로 처리돼 날짜 입력을 방해하는 문제를 발견했다. `static/employee-grid.js`에서 **날짜 입력기의 해당 키 이벤트 전파만 중단**해 네이티브 날짜 입력에 맡겼다. 저장·권한·예약·AI 업무 규칙은 바꾸지 않았다.

새 키보드 회귀 검사와 기존 날짜/원복 검사를 **데모 클러스터의 별도 `test_tm_demo_keyboard` DB**에서 실행해 **2개 통과(5.279초)**했다. 테스트 DB는 제거했고 시연용 `tm_demo` 자료는 보존했다. 첫 회귀 테스트에서 없는 DOM 행 속성을 참조한 오류는 fixture 고객 ID 비교로 수정했으며 첫 실패 로그도 보존했다. 전체435개나92문항 검사를 새로 모두 실행한 결과는 아니다.

근거는 `.local/demo/verification.json`, `keyboard-tests.log`, `keyboard-tests-first.log`, `dev-before.json`, `web.log`·`postgres.log`다. 기존 릴리스 보고서는 당시 버전의 스냅샷으로 유지하며 후속 변경을 표시했다. 현재 데모는 종료하지 않고 실행 상태로 남겼다.
