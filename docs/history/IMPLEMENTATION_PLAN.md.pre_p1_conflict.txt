## 5. 설치·환경 설정 계획

### 5.1 준비 순서

1. TMDB에만 프로젝트 파일을 생성한다. 기존 `.env`, 가상환경, Git 설정, 사용자 파일을 덮어쓰지 않는다.
2. Docker 엔진·Compose v2의 설치 및 데몬 실행을 확인한다. 시스템 설치가 환경 권한 때문에 불가능하면 차단 이유를 기록하고 PostgreSQL 17 + 프로젝트 Python 직접 실행을 보조 경로로 검증한다. 보조 경로 통과를 Compose 검증 통과로 보고하지 않는다.
3. Python 3.13 지원 패치를 프로젝트 전용으로 준비한다. Compose 이미지에 포함하면 호스트 Python은 앱 실행에 필수는 아니다. 호스트 실행용은 `TMDB/.venv`로 분리한다. uv 캐시·관리 Python 경로도 쓰기 가능한 TMDB 내부 또는 임시 경로로 지정한다.
4. PostgreSQL 개발/테스트 DB를 분리한다. 테스트는 폐기 가능한 DB만 사용하고 실제 고객정보·다른 프로젝트 DB에는 접속하지 않는다. 운영 계정·관리형 DB는 필요 없다.
5. Python·JS 테스트 의존성 잠금과 Bootstrap/Tabulator 고정 정적 자산을 준비한다. Playwright 브라우저 바이너리도 별도 설치·검증한다. 설치에는 패키지 다운로드 네트워크가 필요하므로 실패하면 설치 완료로 기록하지 않는다.
6. web·scheduler는 같은 이미지로 구성하고 로컬 바인딩은 loopback으로 제한한다. DB 포트는 기본 비공개로 둔다. 로컬 HTTP 개발 프로필과 운영 HTTPS 설정을 분리한다.
7. `.env.example`에는 가짜 값만 작성하고 실제 `.env`는 추적하지 않는다. 최초 업무 관리자는 전용 관리 명령으로 만들며 `is_superuser`에 의존하지 않는다.

## 6. 설계서 충돌·누락과 해결 시점

기술 구성을 바꿔야 할 근본 모순은 발견하지 못했다. 다음은 확정된 변경이 아니라 검토 결과와 해결 제안이다. 업무 규칙의 해석이 필요한 항목은 해당 기능을 구현하기 전에 명시적으로 결정한다. 현재 계획 작성이나 기반 환경 준비 전체를 막지는 않는다.

## 7. 구현에서 먼저 지킬 정합성

- 모든 업무 쓰기는 공통 transaction-level advisory lock `7420192701`을 거친다. 사용자 ID 정렬 → 전역 설정 → 현장 ID 정렬 → 고객 ID 정렬 → 할당/재콜 순서를 공통 서비스로 보장한다. 읽기·엑셀 파싱은 잠금 밖에서 처리한다.
- 현재 할당은 고객당 하나, PENDING 재콜·삭제 요청도 고객당 하나라는 PostgreSQL 제약을 둔다. 휴지통 포함 현장·연락처 unique를 적용한다.
- 현재 사용자·역할·활성·변경필수 상태·할당 ID·행 버전·삭제 상태를 서버에서 검사한다. 오래된 할당을 새 할당으로 자동 치환하지 않는다.
- 상담 변경·할당 변경·삭제/복구·receipt를 원자적으로 저장한다. 배치 상담 저장은 행별 트랜잭션으로 한 행 실패가 다른 행을 막지 않게 한다.
- 실제 상담 변경만 `first_activity_at`을 최초 기록한다. 조회·삭제 요청 접수·상태 변경·무변경 저장으로 진행을 만들지 않는다. 관리자 수정과 저장 후 원복은 진행으로 남긴다.
- 직원 대기열은 사용자/현장/고객/할당별로 구분하고 전송 스냅샷과 후속 입력을 분리한다. 미확인 자료를 성공으로 제거하지 않는다.
- 수동 회수는 오늘 할당의 진행 건도 포함한다. 23시 자동 회수는 cutoff의 기본 현장·그날 cutoff 이하 현재 할당·미진행만 대상으로 한다. 비활성화 회수는 전 현장·전 날짜 미진행 대상이다.
- 고객/현장 영구 삭제는 이력·후보·응답 캐시의 원문도 지운다. 비식별 처리자/시각/종류/건수 로그와 삭제 원문을 분리한다.

## 8. 로컬 실행 방법 — 최초 계획 이력

다음은 1단계에서 작성한 명령 계약이다. 2단계에서 `manage.py`·Compose·잠금 의존성과 관리 명령을 만들었다. **현재 검증한 직접 실행 경로와 Compose 미검증 범위는 [README](../README.md)를 따른다.** 원래 목표 명령은 이력으로 남긴다.

```sh
cd /Users/hayeon/Documents/TMDB
docker version
docker compose version
```

새 checkout에서만 `.env.example`을 `.env`로 복사해 가짜 개발 값을 채운다. 기존 `.env`가 있으면 복사로 덮어쓰지 않는다.

```sh
docker compose config --quiet
docker compose build
docker compose up -d postgres
docker compose run --rm web python manage.py migrate
docker compose run --rm web python manage.py create_initial_admin
docker compose run --rm web python manage.py seed_demo
docker compose up -d web scheduler
docker compose ps
docker compose logs --tail=100 web scheduler
```

`create_initial_admin`은 대화형으로 가짜 전화번호·이름을 받고 초기 dodream/변경필수 계정을 만든다. `seed_demo`는 로컬·테스트에서만 명시 실행하며 운영 자동 실행은 금지한다. 개발 웹 주소는 `http://127.0.0.1:8000`을 계획하고 실제 Compose 포트와 함께 확정한다. 로그인 → 초기 비밀번호 변경 → 현장 생성 → 가짜 xlsx 업로드 → 분배 → 직원 저장·재콜 → 관리자 회수·삭제 요청 승인 순으로 수동 검증한다.

Docker 사용이 어려우면 Python 3.13 전용 `.venv`와 PostgreSQL 17 명시 경로로 같은 migration·서버·scheduler·테스트를 실행할 보조 절차를 README에 제공한다. SQLite로 동시성 검증을 대체하지 않는다. Django 앱 서버는 운영 시 고정 버전 WSGI 서버와 Caddy 프록시를 사용한다.

백업은 가짜 DB를 dump → 암호화 → 별도 디렉터리에 보관 → 별도 빈 DB로 복원 → 계정·고객·할당·상담·재콜·삭제 상태 정합성 대조한다. 같은 디비의 dump 파일 생성만으로 복구 검증을 통과 처리하지 않는다. 운영 저장소 전송과 HTTPS 검증은 해당 환경에서 따로 검증한다.

각 단계 완료 보고에는 변경 범위, 실제 실행한 명령과 결과, 미실행·실패·제한, 다음 작업을 포함한다. 이후 단계가 필요하다는 이유로 현재 요청 범위를 넘겨 진행하지 않는다.

설계서 17.1은 상담 이력을 AI 구간에서 언급하지만 실제 데이터 누락을 피하려고 **상담 이력 구조는 P1, 저장 연동은 P2부터** 준비한다. 이는 구현 순서를 조정한 것이며 업무 규칙 변경은 아니다. AI 결과 FK는 AI 모델 도입 migration과 함께 연결하고 AI_APPLIED 기능 공개 전에 검증한다. 새 프로젝트에는 과거 BASELINE을 만들 데이터가 없으므로 가짜 과거 이력을 채우지 않는다.

## 5. 첫 실제 구현 단계 P1과 준비사항

아직 수행하지 않은 작업이다. 첫 단계의 결과는 ‘실제 PG에 연결된 로그인 가능한 기반’이며 고객 그리드·AI 생성 기능 전체 완료를 뜻하지 않는다.

1. 원본 해시·프로젝트 상태·AGENTS·Git 루트를 재확인하고 추가 사용자 파일을 보존한다. ZIP은 선별 비교만 하며 덮어쓰기하지 않는다.
2. 기존 ignore 파일이 생겼다면 기존 순서/규칙과 예외를 읽고 병합한다. `.env`, `.env.*`, 두 빈 예시의 예외, `secrets/`, 캐시·venv·Git·백업을 반영한다. 뒤쪽 부정 규칙이 실제 키를 다시 포함시키지 않는지 실제 명령으로 확인한다.
3. Python 3.13 전용 venv와 의존성 lock을 준비한다. uv 배포에 해당 보안 패치가 없으면 공식 소스·해시를 확인해 프로젝트 내부 빌드를 고려한다. 공용 `.venv`·시스템 Python을 변경하지 않는다.
4. PostgreSQL 17 개발/폐기 가능한 테스트 DB를 분리하고 loopback 또는 Compose 내부망만 사용한다. Docker 엔진이 없으면 먼저 준비 가능성을 확인한다. 호스트 PG 실행을 보조 검증하더라도 Compose 빌드/실행 통과로 보고하지 않는다.
5. `.env.example`과 빈 키 `.env.ai.example`을 제공한다. 실제 키는 필요 없다. 로컬 `.env.ai`를 생성해야 하면 빈 값·AI_ENABLED=false·0600으로 만들고 Git/Docker 제외를 먼저 확인한다. 기존 실제 파일은 읽어 출력하거나 덮어쓰지 않는다.
6. 서버 전용 AI 설정 로더·키 없음 fallback·테스트 fake의 운영 차단·기본 availability 상태를 준비한다. 이 단계에서는 외부 AI adapter 호출이나 생성 UI를 제공하지 않는다.
7. UUID 사용자·현장·고객·할당·재콜·업로드·중복 영수증·예약·삭제 요청 모델과 ConsultationRevision의 관계를 설계하고 적용한다. singleton·부분 unique·상태 CHECK·인덱스·순환 FK migration을 검증한다.
8. dodream/변경필수 최초 관리자 명령과 가짜 계정 seed, 로그인·비밀번호 변경·CSRF·역할·세션 버전을 연결한다. 사용자 상태 변경은 회수 규칙까지 원자적으로 처리하는 서비스로만 제공한다.
9. 실제 PG 마이그레이션·역할별 로그인·비밀번호/세션·키 없음 기동·설정 로더·제외 규칙·런타임 프로세스 경계를 테스트하고 기록한다.

P1에는 실제 키·결제 계정·운영 도메인이 필요 없다. 현재 필요한 준비는 Python 3.13, 프로젝트 의존성/Playwright 브라우저 다운로드, Docker/Compose 실행 환경, 로컬 PG/테스트 권한이다. 설치나 DB/브라우저 실행에 환경 권한이 필요한 경우 실제 오류와 수행 범위를 기록한다.

## 6. 기본 업무와 상담 이력의 구현 계약

- 단일 Django 앱을 도메인별로 나누고 Templates+Bootstrap+Tabulator·openpyxl을 사용한다. Redis/Celery/별도 SPA/외부 AI 검색·벡터 DB·음성 인식은 추가하지 않는다.
- 모든 업무 쓰기는 짧은 PG transaction-level advisory lock을 사용한다. 공통 lock → 사용자 ID 순 → 전역 설정 → 현장 ID 순 → 고객 ID 순 → 할당/재콜 순서를 지킨다. 같은 key·다른 본문은 거부한다.
- 현재 할당 하나·PENDING 재콜 하나·PENDING 삭제 요청 하나·휴지통 포함 현장+전화 unique는 PG 제약으로 보장한다. NULL을 포함한 CHECK의 실제 DB 동작도 테스트한다.
- 직원 저장은 customer/assignment/expected_version/mutation으로 행 단위 원자성, 권한 없는 ID는 조회·후보·오류에서 원문을 노출하지 않는다. 관리자도 이름·번호 수정 API 금지다.
- 실제 상담 변경·CustomerChangeEvent·ConsultationRevision·현재 할당 first_activity·버전·mutation receipt는 같은 트랜잭션으로 커밋한다. 무변경·저장 전 원복은 이력/진행을 만들지 않는다.
- ConsultationRevision은 실제 작성자·서버 시각·버전·변경 전후 상담 값과 notes를 보관한다. MANUAL/AI_APPLIED와 IMPORT/BASELINE/SYSTEM_DELETE_NOTE를 구분하고 뒤 세 종류는 직원 실적에서 제외한다.
- 재콜·필드 변경을 통화 횟수로 부르지 않는다. 같은 메모 반복 저장은 고객/작성자/업무 날짜별 최신 유효 메모·의미 있는 변경으로 묶되 원본 revision 근거를 유지한다.
- 삭제 요청 접수만으로 삭제/할당 해제/진행 판정을 하지 않는다. 승인 시 최신 notes에 KST 문구를 한 번만 추가하고 삭제·할당 종료·요청 상태·버전·receipt를 원자적으로 처리한다. 시스템 문구는 일반 notes 길이 한도로 자르지 않는다.
- 이전 앱을 나중에 이관하게 되면 그때만 BASELINE을 1회 만들고 도입 시각·확보 기간을 표시한다. 과거 작성자/날짜를 추측하지 않는다.

## 7. 키 파일·프로세스·테스트 격리 설계

이번에는 이 경계를 구현하지 않았으며 아래는 P1/P12에서 실제 검증할 계약이다.

### 7.1 서버 설정과 실행 경계

- 일반 앱 비밀 설정은 `.env`, 실제 AI 키와 공급자/모델/단가는 `.env.ai`, 공개 예시는 빈 키 `.env.ai.example`로 분리한다. `.env`나 JS의 공개 환경변수에서 AI 키를 대신 받지 않는다.
- web/AI worker 진입점에서만 AI 설정 모듈을 명시적으로 초기화한다. 실제 프로세스 환경변수가 우선이고 파일은 누락값만 보완한다. 기존 환경변수를 덮어쓰지 않는다. `AI_ENV_FILE`로 서버 외부 경로를 지정할 수 있다.
- 같은 이미지여도 일반 회수 scheduler·proxy·PostgreSQL에는 `.env.ai` env_file/볼륨을 연결하지 않는다. scheduler가 공통 Django settings를 import해도 키 파일을 자동 읽지 않게 역할별 로딩을 분리한다. 서버가 결정한 역할만 사용하고 클라이언트가 바꾸지 못하게 한다.
- Compose의 web/AI worker에만 런타임 env_file로 제공한다. Dockerfile의 COPY/ADD/ARG/ENV·빌드 로그·이미지 레이어에 키를 포함하지 않는다. build context는 TMDB로 한정한다.
- Unix 실제 파일은 0600. 파일 없음·빈 키·모델/단가 누락·AI_ENABLED=false면 생성만 `AI_NOT_CONFIGURED`로 막고 기본 업무·기존 결과 조회는 유지한다. 기본 앱 기동을 실패시키지 않는다.
- 프런트에는 기능 사용 가능 여부/설정 필요 상태만 전달한다. 키·프로세스 환경·파일 내용·공급자 인증 헤더·프롬프트 원문을 응답하거나 로그에 출력하지 않는다. 디버그·예외·SDK HTTP 로그에도 마스킹을 적용한다.

### 7.2 fake와 실제 호출 차단

테스트 전용 설정·별도 테스트 DB에서만 fake adapter를 주입한다. DEBUG=true인 일반 개발 서버를 테스트 환경으로 간주하지 않는다. fake를 비테스트 실행에서 선택하면 거부하며 유료 adapter로 자동 fallback하지 않는다.

fake 결과는 테스트 표시(`is_test` 등), 고정 fixture·가짜 source ID, 비용/토큰의 테스트 메타데이터로 구분한다. 테스트 결과를 운영 데이터로 게시·승격하지 않는다. 테스트 실행은 외부 네트워크를 차단하거나 호출 spy로 유료 전송 0회를 보장한다. 실제 키를 fake 테스트 fixture나 sentinel로 사용하지 않는다.

키를 나중에 사용자가 채워도 별도 유료 호출 요청 전에는 이번 개발 검증이 실제 provider를 호출하지 않게 한다. 실제 adapter 연결 검증은 별도 요청을 받은 후 선택한 모델·공식 단가·최대 비용을 확인해 수행할 독립 항목이다. 현재 키·모델 선정은 요구하지 않는다.

### 7.3 키 보호 인수 조건

1. **Git 규칙:** 실제 프로젝트에서 `git check-ignore -v -- .env.ai`는 제외, `.env.ai.example`은 비제외. `.env.ai`가 인덱스에 없어야 한다. 상위 Git 루트를 쓸 때 TMDB 경로로 한정한다.
2. **기존 추적:** 이미 추적 중인 파일을 발견하면 로컬 파일을 유지하면서 인덱스 제외를 처리할 범위를 확인한다. 과거 유출은 비밀값을 출력하지 않고 폐기/재발급 필요를 알린다. 이력 재작성은 별도 영향 검토 없이 하지 않는다.
3. **예시:** AI_API_KEY가 빈 값인지 검사하며 가짜 키조차 예시에 넣지 않는다. 현재 ZIP 예시가 이 조건을 만족하는 것은 확인했다.
4. **Docker:** 실제 규칙과 동일한 격리 빌드에서 비밀이 아닌 sentinel을 사용한다. 제외 후 context와 이미지 각 레이어·history·빌드 메타데이터에 sentinel/실제 키 파일이 없는지 검사한다. COPY 후 삭제로 숨긴 파일도 실패로 처리한다. 실제 기존 키 파일을 테스트용으로 덮어쓰지 않는다.
5. **클라이언트·로그:** HTML/JSON/JS·소스맵·정적 산출물·오류 페이지·로그·fixture·문서에서 sentinel 노출 0건. 발견 시 값 대신 경로/개수만 보고한다. 로그/브라우저 검증에 실제 키 원문을 쓰지 않는다.
6. **프로세스:** key 로더 우선순위·파일 없음 fallback·0600과 web/worker만 수신하는 Compose 구성을 검증한다. scheduler/proxy/postgres가 키를 갖지 않는지 값 출력 없이 확인한다.

임시 Git 저장소 검사는 규칙 자체의 확인에 한정한다. Docker가 없는 호스트에서 YAML만 읽고 context/이미지 검증이 통과했다고 보고하지 않는다. Docker의 제외 규칙과 context 우선순위는 [공식 문서](https://docs.docker.com/build/concepts/context/#dockerignore-files)를 따른다.

## 8. AI 요청·비용·결과의 공통 구현 계약

### 8.1 모델과 예약

19.6의 AIRequest, AIResult, AIQuotaBucket, AIUsageAttempt, AIReportSlot, SiteKnowledge, AIResultSource를 도입한다. `(user,korean_date)`와 `(feature,scope_key,period_key)` unique 및 직원 `successful_count + reserved_count <= 30` DB 제약을 적용한다. 상태·예약 해제·성공 전환은 원자적이고 중복 처리하지 않는다.

AIRequest 상태는 RESERVED/RUNNING/SUCCEEDED/FAILED/CANCELLED/UNKNOWN으로 관리하고 접수 날짜·고정 기간·source fingerprint·prompt/schema/model 버전·provider request ID를 기록한다. AIResult는 검증 JSON·근거 이력·이전 코칭·검토/게시 정보를 보관한다. AIUsageAttempt의 토큰·추론 토큰·단가 버전·예상/확정 비용은 성공 여부와 분리한다.

조직 월 비용의 동시 예약을 위해 월별 예산 원장/요청별 예약 구조도 구체화한다. 이는 기존 모델만으로 부족한 비용 예약을 표현할 기술 구조이며 USD 5 기본값을 바꾸는 업무 변경이 아니다. 금액은 Decimal로 처리하고 요청별 입력·최대 출력·추론 비용과 내부 분할 호출을 모두 예약·합산한다. 비용 귀속 월/정산 방법은 P9에서 명시하고 경계 테스트한다.

AIRequest는 원문 없는 작업 상태와 payload 보관을 구분하고, 사용량/비용은 요청 성공과 독립하여 보존한다. worker는 기존 DB 큐와 같은 앱 이미지를 쓰며 별도 Redis/Celery를 추가하지 않는다. account 1개·global 외부 호출 2개의 기본 제한을 DB 예약/claim으로 검사하고 중단·lease 만료는 UNKNOWN 정책과 함께 처리한다.

### 8.2 요청 흐름

1. 버튼 요청 전에 해당 행을 일반 저장한다. 실패하면 새 AIRequest/차감/예약을 만들지 않는다. 다른 행의 100초 타이머는 유지한다.
2. 서버가 로그인·비밀번호 변경·역할·현재 담당·할당 ID·expected_version·삭제·요일·AI 설정을 검사하고 입력을 DB에서 구성한다. 클라이언트의 임의 prompt/provider/model/key/분석 대상 원문을 받지 않는다.
3. 같은 idempotency key/본문은 기존 작업을 반환하고 다른 본문은 충돌이다. 유효 캐시 키에는 권한·할당·버전·기준 날짜·기간·prompt/schema/model 버전을 포함한다. 캐시 재조회는 새 비용/직원 횟수 없음.
4. 짧은 공통 쓰기 트랜잭션에서 quota 또는 report slot, 조직 비용·처리 중 제한을 예약한다. 날짜·cutoff·week_start_date는 접수 시 KST로 고정한다. 서버 시각만 신뢰한다.
5. **트랜잭션 종료 후** worker가 외부 I/O를 수행한다. 공통 advisory lock/고객 행 잠금을 네트워크 대기 동안 유지하지 않는다. worker는 이미 접수된 작업만 처리하고 새 생성 작업을 스스로 만들지 않는다.
6. schema·enum·출력 길이·source ID·근거·입력 fingerprint·현재 권한을 검사한다. 응답을 HTML/코드/SQL로 실행하지 않고 외부 도구·URL·DB 수정 권한을 모델에 제공하지 않는다.
7. 유효 결과 저장과 예약→성공 전환을 원자적으로 처리한다. 회수/재분배/삭제/비활성화 시 결과 노출을 취소하고 횟수 예약을 반환하되 발생 비용은 남긴다. 버전 변경은 오래된 결과로 표시하고 자동 적용을 막는다.
8. 확실한 실패는 예약을 1회 해제한다. 불명확한 timeout은 UNKNOWN으로 두고 자동 유료 재호출하지 않는다. 10분 확인 상한 후 실패 종료·사용자 예약 반환·보수적 비용 유지. 늦은 응답으로 종료 작업을 성공 전환/적용하지 않는다.

직원 횟수는 접수일 기준이며 자정 후 완료도 그 bucket을 정산한다. 공급자 실패·오류 schema 등 과금된 시도 비용과 사용자 성공 횟수는 별도 지표다. 가격 설정이 없거나 예산 소진이면 생성만 막는다. 월 예산은 공급자의 절대 청구 상한을 보장하지 않는다.

### 8.3 직원 세 기능·추천 적용

CLEANUP은 정리 메모/추천 필드, SUMMARY는 상담 핵심/약속/확인점, NEXT_QUESTIONS는 근거가 있는 질문 3~5개를 반환한다. 고객명·번호·담당자·내부 ID·삭제 상태는 추천 변경 대상이 아니다. 근거 부족은 NO_SUGGESTION, null은 기존 값 삭제 지시가 아니다.

모든 추천은 기본 미선택이고 직원이 선택 적용해야 기존 편집 대기열로 들어간다. notes 교체 전 원문/제안 비교, 일반 batch-update와 mutation/버전/할당 검사·source_ai_result_id·AI_APPLIED revision을 사용한다. SUMMARY/질문은 읽기 전용이다. 생성·조회는 진행이 아니고 실제 변경 저장만 진행이다. 과거 메모의 상대 날짜는 원문 작성 시각과 접수 KST를 함께 해석하고 모호한 날짜·가격·계약 여부는 확인 필요로 남긴다.

19.9의 ‘요청자 또는 권한 있는 관리자’는 모든 AI 결과의 관리자 우회를 뜻하지 않는다. 19.2/19.6의 상세 접근 규칙에 따라 직원 고객 결과는 요청 직원+현재 담당/할당 검사를 지키고, 관리자 공용 보고서·관리자 전용 코칭·게시 가이드는 각각 별도 조회 범위를 적용한다.

### 8.4 팀장 세 기능

- **주간 브리핑:** 일요일 서버 접수만 허용. 조직 GLOBAL + 월요일 날짜 unique, 월요일 00:00~일요일 접수 cutoff를 표시하고 월요일 완료에도 범위를 유지한다. 비활성 사용자를 포함한 실제 직원/관리자 업무, 고객 반응·거절 사유, 상담 기록 검토 보조, 다음 확인 업무를 포함한다. 날짜 비어 있음은 허용된 업무 값이므로 확인 필요를 강제 오류로 바꾸지 않는다.
- **직원 코칭:** 실제 작성자·작업 시각 기준으로 전체 현장의 직전 30×24시간과 이전 코칭을 분석한다. 현 담당자에게 과거 실적을 귀속시키지 않는다. 최근 3개와 그 이전 과제, 비교 기간·근거 수를 표시한다. 최초/기록 부족/비교 불가는 명시하고 말투·성격·순위·개선 원인을 추측하지 않는다. 관리자만 조회하고 직원에게 자동 발송하지 않는다.
- **팀 가이드:** 현장 최근 30일 + 유효한 관리자 검토 SiteKnowledge만 상품 사실 근거로 사용한다. 안내자료 없으면 질문/확인 순서만 만들고 가격·혜택 등은 담당자 확인 필요로 둔다. DRAFT→검토/수정→PUBLISHED, 직원은 해당 현장 게시본만 조회한다. 새 초안 중 기존 게시본 유지. 수정·게시·조회는 AI 호출/횟수 차감 없음. 고객 식별정보·개별 상세·직원 코칭 본문은 제외한다.

정량 집계는 전체 범위를 서버 SQL로 계산한다. AI는 근거 source별 분류/서술만 맡는다. 이름·전화·로그인·키는 모델 입력에서 제외하고 메모의 직접 식별값도 가능한 범위에서 제거한다. 입력 초과 시 유효 캐시→분산 표본 순으로 처리하고 전체 n/분석 m, 표본 여부를 표시한다. 표본 비율을 전체 비율로 제시하지 않는다. 입력에 없는 source ID와 모델 임의 URL은 제거하고 링크는 서버 권한 경로로만 생성한다.

### 8.5 영구 삭제와 파생 결과

원본 삭제 전에 AIResultSource의 전이 참조 집합을 모으고 같은 도메인 삭제 트랜잭션에서 원본·캐시·직원 결과 원문을 삭제한다. 혼합 브리핑/코칭/가이드와 이를 재참조한 코칭 등의 본문은 재귀 무효화·제거한다. 방문 집합으로 반복 처리를 막고 게시 가이드는 해제한다. 직원/관리자에게 원본 삭제로 제공 불가를 표시한다.

사용 횟수·토큰·비용·생성 시각 같은 비원문 메타데이터는 유지하고 이미 쓴 quota/성공 slot/비용을 환불하지 않는다. 원본이 삭제된 코칭은 다음 입력에서 제외한다. 새 유료 생성은 자동 수행하지 않는다. 타 현장의 같은 번호까지 삭제하지 않는다. 휴지통 이동만으로는 영구 삭제하지 않되 직원 AI 접근은 막는다.

## 9. 설계서 교차 문구·누락·준비 문제

현재 계획 또는 P1을 막아 질문이 필요한 업무 충돌은 없다. 다음 사항은 이미 명시된 특례를 적용하거나 해당 단계에서 기술 기본값을 기록하여 해결할 수 있다. 설계서 원문은 수정하지 않는다.

| 항목·근거 | 영향과 처리 계획 |
|---|---|
| 실제 .env.ai 미포함 (20.1/전달안내) | 원본 문서/패키지 불일치 안내. 예시만 전달하고 P1에 대상 환경에서 빈 파일 생성. 실제 키 요청 불필요 |
| 관리자 수동 저장/공통 이동 전 저장 (6.3/7.2) | 관리자 이동에 저장/머무르기/명시적 폐기 선택을 제공하여 수동 저장을 유지. 직원은 기존 즉시 전송 규칙. 무확인 관리자 자동 저장으로 바꾸지 않음 |
| notes 10,000자/승인 문구 (6.1/7.8) | 승인 시스템 추가분과 복구 후 기존 길이 예외를 적용. DB text를 자르거나 승인 실패로 바꾸지 않음 |
| 미할당 관리자 이력 (13.6/19.6) | 고객 이력과 assignment=null의 ConsultationRevision은 남기되 새 할당 진행·직원 실적으로 소급하지 않음 |
| 작업 조회 관리자 표현 (19.6/19.9) | 상세 결과별 권한을 우선 적용. 직원 개인 고객 결과의 관리자 일괄 우회를 허용하지 않음 |
| 생성은 버튼만/worker (18.8/19.7) | 버튼만 새 작업 생성. worker의 접수 작업 실행과 상태 GET을 구분. 화면/자동 저장/스케줄러가 새 유료 작업을 만들지 않음 |
| 업로드 FAILED 재시도 (12.2/13.7) | P3에 상태·같은 key·TTL·치명 오류 롤백 계약 구체화. 성공 결과 재시도 건수는 고정 |
| 누락 예약 시작일·lease·timeout (9.4/16.1) | 운영 시작일/유실 실행 범위·lease·상한 재시도를 P6에 설정화. 과거 날짜 임의 생성/무한 RUNNING 방지 |
| 월 예산 귀속·단가/추론 토큰·입력 cap (19.7~19.8) | P9에 KST 월 경계·접수월 예약/정산 정책·실제 모델 한계를 문서화. 모델/단가 미지정은 유료 생성 비활성으로 처리 |
| 미진행 통계 집합·결과 보존·성능 합격선 | 해당 통계/업로드/성능 단계에 전체/오늘 구분 라벨·정리 기간·측정 환경/수치를 명시. 근거 없는 SLA/통화 횟수를 만들지 않음 |
| Python 3.13·Docker 미준비 | P1 설치·실행 검증 필요. PG 호스트 실행과 Compose 실행 결과를 분리. 이번 계획 단계에서 설치하지 않음 |

AI 공급자/모델/운영 도메인/백업 목적지가 아직 없어도 기본 앱·fake 기반 테스트는 진행 가능하다. 실제 유료 모델 품질·공식 가격·지원 종료·청구 단위 검증은 유료 호출 허용 전 별도 수행한다.

### 10.3 구현 후 제공할 실행 계약

**현재 manage.py·Compose·테스트가 없으므로 아래 명령은 아직 실행할 수 없다.** P1 이후 실제 만든 진입점과 검증한 명령으로 README를 제공한다.

```sh
cd /Users/hayeon/Documents/TMDB
docker compose config --quiet
docker compose build
docker compose up -d postgres
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py create_initial_admin
docker compose run --rm web python manage.py seed_demo
docker compose up -d web scheduler
```

가짜 계정 seed는 개발/테스트에서만 명시 실행한다. 최초 관리자 계정과 seed의 예제 관리자 생성이 충돌하지 않게 순서/선택 방법을 README에 구분한다. AI worker는 구현 후 web과 같은 이미지로 기동하고 `.env.ai`의 빈 키/비활성 상태에서 유료 호출하지 않는다. 호스트 Python+PG 보조 실행법도 제공하되 SQLite로 경합 검증을 대체하지 않는다.

```sh
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test --noinput
```

Django 테스트는 폐기 가능한 별도 PG DB를 사용하고 독립 연결·TransactionTestCase·barrier로 경합을 검증한다. 브라우저는 Playwright로 별도 관리자/직원·다중 탭·시간 경계·오프라인을 확인한다. fake 실행에는 테스트 전용 설정·네트워크 차단을 적용한다.

백업 검수는 가짜 DB dump·암호화·다른 빈 DB 복원 후 사용자·고객·할당·상담 revision·재콜·삭제 요청·AI quota/비용/무효화 상태를 대조한다. 같은 볼륨 복사를 별도 백업으로 보고하지 않는다. 실제 외부 저장소 전송·운영 HTTPS·유료 호출·배포의 미실행 상태를 분리한다.
