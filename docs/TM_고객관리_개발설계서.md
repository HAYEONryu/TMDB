# TM 고객관리 웹사이트 개발설계서

- 문서 버전: 2.0 (AI 기능 통합 최종본)
- 작성일: 2026-10-27, 한국 시간
- 수정일: 2026-11-03, 한국 시간
- 용도: 개발 에이전트에게 전달할 구현 기준 및 인수 검수 기준
- 상태: 사용자가 승인한 요구사항 반영 완료. 실제 사이트 구현·배포는 이 문서의 산출 범위가 아니다.
- 기준: 대화에서 마지막으로 승인한 조건이 최초 요구사항보다 우선한다.
- v2.0 추가: 직원 AI 3종·직원별 하루 30회, 팀장 AI 3종, 상담 본문 이력, 사용량·비용 제어, API 키 전용 파일·Git/Docker 제외 규칙.
- 직원 30회 제한·버튼 실행·일요일 주간 브리핑·30일 직원 코칭은 사용자 지정 조건이다. 성공 시 차감·팀장 생성 횟수·분석 범위 등 추가 제안은 19장의 조정 가능한 구현 기본값으로 구분한다.

## 1. 개발 에이전트에게 전달할 지시

이 문서를 기준으로 한국어 TM 고객관리 웹사이트를 구현한다. 정적 화면 시안만 만들지 말고 로그인, 권한 검사, PostgreSQL 저장, 엑셀 업로드, 분배·회수, 자동 저장, 예약 작업, 직원·팀장 AI 기능까지 연결한다.

1. 기존 저장소와 AGENTS.md를 먼저 읽는다. `sources/` 아래 자료는 읽기 전용이며 수정하지 않는다.
2. 승인된 업무 규칙을 임의로 변경하지 않는다. 이 문서의 `구현 기본값`은 미지정 세부사항을 구체화한 선택이며 설정으로 조정할 수 있게 한다.
3. 기존 애플리케이션이 있으면 구조를 우선 존중한다. 새 프로젝트라면 3장의 기술 구성을 사용한다.
4. 한 애플리케이션 안에서 도메인별로 코드를 나눈다. 초기 구현에 Redis, Celery, Kubernetes, 별도 SPA, 마이크로서비스를 추가하지 않는다.
5. 디비 제약·트랜잭션·서버 권한 검사를 구현한다. 화면의 버튼 비활성화만으로 업무 규칙을 보장하지 않는다.
6. 회수·재분배·자동 저장 간 경합, 중복 요청, 재시도를 먼저 설계하고 구현한다.
7. 18장의 필수 검수 시나리오를 테스트한다. 동시성 검증에는 실제 PostgreSQL을 사용한다.
8. 가짜 데이터로 실행 가능한 개발 환경, 마이그레이션, 환경변수 예시, 배포·백업·복구 문서를 제공한다.
9. 유료 서비스 신청과 실제 운영 서버 배포는 별도 사용자 승인 없이 수행하지 않는다.
10. 최종 보고에는 구현 범위, 실행 방법, 검증 결과, 남은 제한을 포함한다.
11. AI 기능의 상세 업무 규칙은 19장, API 키 분리와 저장소 제외는 20장을 따른다. 실제 키 없이도 기존 업무와 가짜 AI 응답을 이용한 테스트가 실행되어야 한다.
12. 이미 구현한 프로젝트라면 전체를 다시 만들지 말고 현재 코드·마이그레이션과 비교하여 필요한 변경만 적용한다. 기존 상담 기록을 근거 없이 소급 생성하지 않는다.

## 2. 목적·용어·운영 범위

### 2.1 목적

현장별 고객정보를 업로드하고 직원에게 분배하여 상담·방문·계약 진행상황을 관리한다. 소규모 운영에 맞춰 비용과 유지보수 부담을 줄인다.

### 2.2 용어

| 용어 | 정의 |
|---|---|
| DB | 고객정보 한 건 또는 여러 건. UI에서는 `DB`를 이 의미로 사용한다. |
| 디비 | 데이터베이스 개념. 기술 문서에서는 PostgreSQL 등 저장소를 뜻한다. |
| 현장 | DB를 구분하는 카테고리 |
| 관리자·팀장 | 동일한 역할. 모든 현장을 공유하고 관리한다. |
| 직원·팀원 | 본인에게 현재 배정된 DB를 처리하는 사용자 |
| 현재 할당 | DB와 담당자 사이의 현재 유효한 배정 관계 |
| 진행·수정 이력 있음 | 현재 할당 이후 상담 관련 값의 실제 변경이 서버에 한 번 이상 저장됨 |
| 미진행 | 현재 할당 이후 상담 관련 실제 변경의 서버 저장 이력이 없음 |

`미진행`은 통화결과가 비어 있다는 뜻과 다르다. 주택상황이나 상담내용 하나만 변경해도 진행으로 본다. 반대로 업로드 당시 통화결과가 있더라도 새 할당 이후 수정 이력이 없으면 그 할당은 미진행이다.

### 2.3 운영 조건

- 전체 사용자·동시접속자 약 20명 이하, 관리자 5명 미만.
- 수십 개 현장, 현장별 수백 건 이상. 최소 수만 건 규모를 고려한다.
- 주 사용 시간 10:00~18:00. 이 시간 밖의 사용을 차단하지 않는다.
- 모든 업무 날짜와 예약 실행 기준은 `Asia/Seoul`이다.
- PC 브라우저 중심. 한국어 UI. 좁은 화면에서는 그리드 가로 스크롤을 허용한다.
- 앱 서버 한 대로 시작하며 장애·배포 중 짧은 중단을 허용한다.
- IP·접속 기기 제한은 구현하지 않는다.
- 직원 그리드의 복사·우클릭을 제한하고 직원에게 엑셀·CSV 내보내기를 제공하지 않는다.
- 개인정보 컴플라이언스 전용 화면, DLP·VDI, SMS·전화 발신, 녹취, 모바일 앱은 초기 범위에 포함하지 않는다.
- 사내 사용이라도 로그인·권한 검사·비밀번호 해시·HTTPS·기본 로그 보호는 일반적인 시스템 기본 기능으로 구현한다. 이 문서는 법적 준수 충족을 인증하는 문서가 아니다.

## 3. 기술 구성과 운영 환경

### 3.1 기본 기술

| 영역 | 구성 |
|---|---|
| 서버 | Django 5.2 LTS, 구현 시점의 지원 중 최신 보안 패치 적용 |
| 언어 | Python 3.13의 지원 중 패치 버전. 라이브러리 호환성을 확인해 고정 |
| 디비 | PostgreSQL 17의 지원 중 패치 버전. 버전은 설치 시 지원 상태 확인 |
| 화면 | Django Templates + Bootstrap 5 + 필요한 JavaScript 모듈 |
| 그리드 | Tabulator. 셀 편집·선택·서버 페이지 조회·열 필터 구현 |
| 엑셀 | openpyxl, `.xlsx`만 지원 |
| 인증 | Django 서버 세션, CSRF 보호, 기본 해시 기반 비밀번호 관리 |
| 실행 | Docker Compose, 웹 앱과 예약 작업은 같은 이미지 사용 |
| 프록시 | Caddy 등 HTTPS 종료가 가능한 단일 프록시 |
| 테스트 | Django 테스트 + PostgreSQL, 핵심 브라우저 흐름은 Playwright |

장기 지원 종료 전에 업그레이드를 계획한다. `latest` 이미지 태그와 버전 미고정 의존성을 운영에 사용하지 않는다. 일반 업무 관리자를 Django의 `is_superuser`로 만들지 않는다.

### 3.2 최소 비용 배포 기본값

다음은 승인된 `앱 서버 한 대·최소 비용`을 구체화한 **구현 기본값**이다.

- 서울 또는 한국과 가까운 리전의 Linux VM 한 대.
- 초기 검토 자원: 2 vCPU, 메모리 4GB, SSD 40GB 이상. 성능 보장치가 아닌 출발점이다.
- 최소 비용 프로필: 같은 VM에 `proxy`, `web`, `postgres`, `scheduler`를 Compose로 실행한다. PostgreSQL은 영속 볼륨을 사용한다.
- 앱과 디비가 함께 중단될 수 있다는 제한을 운영 문서에 명시한다.
- 디비 관리 부담을 줄일 예산이 확보되면 PostgreSQL만 관리형 서비스로 옮긴다. `DATABASE_URL` 변경으로 전환 가능하게 한다.
- 디비 포트는 인터넷에 공개하지 않는다. 웹 프록시의 80/443만 서비스에 사용한다.
- 매일 별도 저장소에 암호화된 디비 백업을 보관한다. 같은 VM의 볼륨 복사만으로 백업을 대체하지 않는다.
- 백업 기본 보관 7일, 일일 백업 기준 최대 약 24시간 데이터 손실 가능성을 명시한다. 이는 구현 기본값이며 복구 목표에 맞춰 변경할 수 있다.
- 유료 인프라 비용은 공급자·리전·백업·트래픽에 따라 달라지므로 문서에서 고정 금액을 보장하지 않는다.
- 로컬 실행은 외부 계정 없이 가능해야 한다. 운영 도메인과 백업 저장소 자격증명은 환경변수로 받는다.

### 3.3 코드 구조 예시

```text
config/                 설정·URL·로깅
apps/accounts/          사용자·로그인·세션 무효화
apps/sites/             현장·전역 기본 현장
apps/customers/         DB 조회·수정·삭제·복구
apps/assignments/       분배·회수·진행 판정
apps/callbacks/         재콜 일정·완료 이력
apps/imports/           엑셀 검증·확정·결과
apps/dashboard/         관리자·직원 통계
apps/operations/        요청 중복 방지·예약 실행·업무 이력
apps/ai_assistant/      AI 요청·결과·한도·비용·공급자 연동
apps/consultations/     상담 본문·항목 변경 이력
templates/              한국어 화면
static/js/              그리드·저장 대기열·IndexedDB
tests/                  통합·동시성·브라우저 검증
docs/                   배포·운영·복구 설명
```

파일별 함수가 지나치게 분산되지 않도록 한다. API·관리자 직접 변경·예약 작업이 같은 도메인 서비스를 호출하게 하여 규칙을 중복 구현하지 않는다.

- 직원에게 타인의 DB가 목록·상세·필터 후보값·오류 응답을 통해 노출되지 않게 한다.
- 권한은 매 요청마다 서버에서 확인한다. 직원이 임의의 `employee_id`를 보내도 조회 범위를 넓힐 수 없다.
- 관리자도 고객명·연락처 수정은 불가하다. 화면 비활성화 외에 API에서 거부한다.
- 관리자·직원 모두 할당 시각, 진행 판정 시각, 내부 ID, 삭제 여부를 일반 셀 수정으로 바꿀 수 없다.
- 사용자는 삭제하지 않고 비활성화한다. 이력의 사용자 참조를 유지한다.
- 마지막 활성 관리자의 비활성화·직원 전환은 차단한다. 이는 관리자 계정 부재 방지를 위한 구현 기본값이다.

## 5. 공통 UI·현장 선택

### 5.1 공통 레이아웃

- 좌측 메뉴, 상단 현장 선택, 사용자 이름·역할·로그아웃 영역.
- 관리자 메뉴: 대시보드 / DB 관리 / DB 분배·회수 / 휴지통 / 사용자 관리.
- 직원 메뉴: 대시보드 / 오늘의 DB / 나의 DB.
- 폼 오류는 항목 옆에, 작업 결과는 알림 또는 모달로 표시한다.
- 요청 처리 중 해당 실행 버튼을 비활성화한다. 서버에서도 중복 요청을 방지한다.
- 한국어 날짜 표시는 `YYYY-MM-DD (요일) HH시mm분`, 할당일 축약 표시는 `MM/DD`. 연도 포함 값은 툴팁·상세 표시로 제공한다.

### 5.2 전역 기본 현장

- 관리자가 대시보드에서 변경하면 한 개의 전역 설정을 갱신한다.
- 모든 현장 선택창은 새 화면 진입 시 전역 기본 현장으로 초기화한다.
- 사용자가 화면 안에서 다른 현장을 고르는 것은 전역 기본 현장을 바꾸지 않는다.
- 다른 관리자가 기본 현장을 변경해도 이미 작업 중인 화면은 자동 전환하지 않는다.
- 다음 화면 진입·새로고침 시 최신 기본값을 사용한다. 별도 URL에 명시한 현장이나 현장 생성 직후 이동은 예외로 해당 현장을 연다.
- 전체 현장 목록은 직원도 선택할 수 있으나 고객정보 조회는 본인 담당 범위로 제한한다.
- 현장이 없으면 빈 상태와 관리자용 `현장 생성` 버튼을 표시한다. 직원에게는 `등록된 현장이 없습니다`를 표시한다.
- 현재 선택 현장이 삭제되면 서버는 작업을 거부하고 미전송 자료를 충돌 상태로 표시한다. 다른 현장에 자동 저장하지 않는다.

## 6. 그리드 열·입력 규칙

### 6.1 업무 열 순서

체크박스·할당일·저장 상태·행 작업 같은 시스템 열은 아래 업무 열과 구분하며 엑셀 매핑에 포함하지 않는다.

| 순서 | 제목 | 내부 필드 | 타입·허용값 | 등록/수정 |
|---|---|---|---|---|
| 1 | 담당직원명 | assignee | 활성 직원 선택, 미할당은 빈 값 | 업로드는 빈 값, 관리자만 별도 변경 |
| 2 | 고객명 | customer_name | 필수 문자열, 양끝 공백 제거, 최대 100자 | 최초 등록만 |
| 3 | 고객 연락처 | phone_normalized | 필수, 정규화 후 010으로 시작하는 11자리 | 최초 등록만 |
| 4 | 통화결과 | call_result | 빈 값 / 부재 / 거절 / 관심 / 재통화 / 방문예약 / 방문 / 재방 | 상담 수정 |
| 5 | 방문예약 날짜 | visit_at | 빈 값 또는 시간대 있는 일시 | 상담 수정 |
| 6 | 계약여부 | contract_status | 미확인 / 미계약 / 계약, 기본 미확인 | 상담 수정 |
| 7 | 상담기타내용 | notes | 빈 문자열 허용, 여러 줄, 최대 10,000자 | 상담 수정 |
| 8 | 재콜일정 | callback_due_at | 빈 값 또는 시간대 있는 일시 | 상담 수정·별도 완료 |
| 9 | 주택상황 | housing_status | 자유 문자열, 최대 200자 | 상담 수정 |

- 주택상황 placeholder: `미확인 / 자가 / 전세 / 월세 / 기타`. 선택형으로 강제하지 않는다. 빈 값도 허용한다.
- 방문예약·재통화 등 어떤 통화결과에서도 방문예약·재콜 날짜는 비어 있을 수 있다.
- 열기만 하거나 포커스를 옮긴 것은 수정이 아니다. 정규화한 새 값이 서버 값과 다를 때만 실제 변경이다.
- 문자열은 HTML로 렌더링하지 않는다. 상담내용은 일반 텍스트로 표시한다.
- 계약여부 `미확인`과 빈 값은 서버에서 같은 기본값으로 정규화한다.
- 날짜는 화면·엑셀에서 한국 시간으로 해석하고 디비에는 UTC 기준 timezone-aware 값으로 저장한다.

### 6.2 연락처

- 숫자 자료형으로 저장하지 않는다. `01012345678` 문자열로 저장하고 `010-1234-5678`로 표시한다.
- 하이픈·공백을 제거한 뒤 `^010[0-9]{8}$`를 만족해야 한다. 그 밖의 문자는 무조건 제거하지 말고 잘못된 값으로 안내한다.
- `+82`, 일반전화, 다른 휴대전화 앞번호는 초기 범위에서 허용하지 않는다.
- 내부 UUID를 기본키로 사용한다.
- 삭제 여부와 관계없이 `(site_id, phone_normalized)`에 유일 제약을 적용한다.
- 서로 다른 현장에는 같은 연락처를 등록할 수 있다.
- 고객명·연락처 오입력은 관리자 개별 영구 삭제 후 재등록한다. 상담정보·연결 이력 손실을 확인받는다.

### 6.3 검색·필터·페이지

- 고객명 또는 연락처 검색. 전화번호 검색 입력의 하이픈은 정규화한다.
- 필터는 열 제목의 메뉴에서 값 체크·전체 선택·초기화를 제공한다. 날짜는 범위, 긴 상담내용은 포함 검색으로 제공한다.
- 여러 열 필터는 AND, 같은 열의 여러 선택값은 OR로 결합한다.
- 필터 후보값도 현재 사용자·선택 현장·현재 화면의 권한 범위에서 생성한다.
- 서버가 필터·정렬·페이지를 적용한다. 브라우저에 전체 현장 데이터를 한 번에 전달하지 않는다.
- 기본 50행, 선택 50/100행, 최대 100행. 기본 정렬은 생성 시각 내림차순 + ID로 안정화한다.
- 페이지 전체 선택은 현재 페이지에만 적용한다. 필터 결과 전체 선택 기능은 초기 범위에서 제외한다.
- 미저장 값은 필터 적용·페이지 변경 전에 저장한다. 실패 시 현재 화면에 남아 재시도 또는 변경 폐기를 선택하게 한다.

## 7. 관리자 화면

### 7.1 메인 대시보드

- 전역 기본 현장 선택 및 `기본 현장 설정` 버튼.
- 현장 선택 변경만으로 통계를 조회하고 설정 버튼을 눌렀을 때만 전역 기본값을 변경한다.
- 선택 현장의 전체 DB·미할당 DB·휴지통 DB 수.
- 활성 직원별 표: 오늘 할당 건수 / 현재 보유 전체 건수 / 오늘 할당분 중 현재 보유 건수 / 오늘 할당분의 통화결과별 건수 / 미진행 건수.
- 오늘 할당 건수는 할당 이력을 기준으로 한다. 같은 DB가 같은 직원에게 오늘 여러 번 배정되어도 기본 수치는 고유 DB 수로 표시하고, 총 할당 작업 횟수와 혼동하지 않게 한다.
- 오늘 진행현황은 `오늘 그 직원에게 할당된 고유 DB 집합` 중 현재도 그 직원이 보유하는 DB의 현재 통화결과로 집계한다. 회수·이관된 DB 수는 별도 표시한다.
- 비활성 직원이 보유한 진행 DB가 있으면 이관 필요 목록에 표시한다.
- 통계 자동 폴링은 기본 사용하지 않는다. 화면 진입·사용자 새로고침 시 조회한다. 삭제 요청 알림만 7.8의 경량 조회 규칙을 적용한다.
- `이번 주 AI 브리핑` 버튼과 기존 브리핑 조회 영역을 추가한다. 생성 버튼은 한국 시간 일요일에만 활성화한다.
- 직원별 행에 `AI 코칭` 버튼과 이전 코칭 조회를 제공한다.
- 관리자 메뉴에 `팀 상담 가이드`를 추가한다. 선택 현장 기준 생성·검토·수정·게시를 지원한다. 자세한 범위와 한도는 19장을 따른다.

### 7.2 DB 관리

- 현장 선택 즉시 조회. 별도 조회 버튼 없음.
- 버튼: 현장 생성 / 엑셀 업로드 / 선택 삭제 / 저장 / 현장 삭제.
- 직원 화면과 달리 관리자 셀 편집은 `저장` 버튼으로 확정한다. 화면 이동 시 미저장 안내를 한다.
- 담당직원 셀의 변경은 일반 저장과 분리된 재분배·회수 확인으로 처리한다. 이미 편집 중인 상담 값이 있으면 먼저 저장하거나 취소하게 한다.
- 고객명·연락처는 읽기 전용. 상담 관련 열은 수정 가능.
- 선택 삭제 확인: `n개의 정보를 삭제하시겠습니까?` / 삭제 / 취소.
- 삭제 시 `deleted_at`, 삭제자, 삭제 작업 시각을 저장한다. 통화결과와 상담정보는 유지한다.
- 삭제 DB는 일반 조회·분배·직원 화면·재콜 목록에서 제외한다.
- 소프트 삭제 시 현재 할당은 종료하되 할당 이력은 남긴다. 복구해도 이전 담당자를 자동 복구하지 않는다. 이는 오래된 배정을 재활성화하지 않기 위한 구현 기본값이다.

### 7.3 현장 생성 모달

- 입력: 현장명, 최대 100자. 양끝 공백을 제거하고 빈 값은 거부한다.
- 중복 비교는 공백 제거 후 영문 대소문자를 구분하지 않는 정규화 키로 한다. 디비 유일 제약도 적용한다.
- 중복 메시지: `이미 존재하는 현장명입니다.`
- 성공하면 생성한 현장의 DB 화면으로 이동한다. 전역 기본 현장은 자동 변경하지 않는다.
- 최초 현장만 전역 기본 현장으로 자동 지정한다.

### 7.4 DB 분배·회수

1. 현장 선택 → `확인` → 현재 분배 가능 잔여 수 조회.
2. 직원 선택: 첫 항목 `전체 팀원`, 이후 활성 직원. 관리자는 제외한다.
3. 직원당 분배 수량 입력 → `분배`.
4. 현장을 바꾸면 이전 잔여 수·확인 상태를 초기화하고 수량 입력·분배를 비활성화한다.
5. 잔여 확인은 참고값이다. 분배 실행 시 서버에서 다시 검증한다.

분배 가능 조건은 `같은 현장 AND 삭제되지 않음 AND 현재 담당자 없음`이다. 초기 범위에 별도 수신거부·보유기간 필터를 임의 추가하지 않는다.

- 수량은 양의 정수만 허용한다.
- 전체 팀원은 실행 트랜잭션 안에서 확정한 활성 직원 목록이다.
- `선택 직원 수 × 직원당 수량`만큼 서로 겹치지 않는 DB를 랜덤 배정한다.
- 랜덤은 균등 후보 추출을 기본으로 하며 고객 속성별 가중치는 없다. 현재 데이터 규모에서는 PostgreSQL 랜덤 추출을 사용해도 되며 실행 시간을 측정한다.
- 부족하면 아무것도 배정하지 않는다. `n개씩 분배할 수 있습니다.`를 alert로 표시한다.
- `n = floor(실행 시점 잔여 수 / 대상 직원 수)`. 개별 직원은 대상 수 1이다.
- 직원이 0명이면 `분배할 활성 직원이 없습니다.`를 표시하며 나눗셈하지 않는다.
- 성공 시 총 배정 수와 직원별 수량을 표시하고 잔여 수를 갱신한다.
- `전체 팀원` 회수도 지원한다. 실행 시점 활성 직원 전체의 대상 DB를 회수한다. 이는 최초 화면의 전체 팀원 선택을 구체화한 구현 기본값이다.
- 수동 회수는 선택 현장에서 선택 직원에게 **현재 할당되어 있고 할당일이 오늘인 DB 전체**이다. 진행 여부와 관계없이 회수한다.
- 회수 전에 대상 수 확인 모달을 표시한다. 실제 실행 시 다시 계산하고 최종 결과를 표시한다.
- 비활성 직원의 진행 DB는 DB 관리의 담당직원 변경으로 이관·회수할 수 있다.

### 7.5 휴지통

- 현장 선택 즉시 그 현장의 삭제 DB를 조회한다.
- `전체 현장` 필터를 추가해 모든 삭제 DB도 조회할 수 있다. 최초값은 전역 기본 현장이다.
- 검색·열 필터·현재 페이지 체크박스 선택 지원.
- 복구: 삭제 표지만 해제하고 상담정보를 유지한다. 담당자는 미할당 상태이다.
- 개별 영구 삭제: 관리자만 가능. `고객정보와 상담·할당·재콜 이력이 삭제되며 되돌릴 수 없습니다` 확인 후 실행한다. 영구 삭제는 휴지통 DB에만 제공한다.
- 영구 삭제 후 동일 현장·연락처로 새 DB 등록 가능. 새 내부 ID를 생성한다.
- 감사용으로 작업 종류·처리자·시각·건수만 남길 수 있으나 삭제된 고객의 원문·내용·이력은 보존하지 않는다.

### 7.6 현장 영구 삭제

- 관리자만 가능. 현장명을 정확히 입력하고 삭제 버튼을 누르게 한다.
- 메시지: `현장과 관련 고객정보 및 상담·할당·재콜 이력이 영구 삭제됩니다. <현장명> 현장을 삭제하시겠습니까?`
- 모든 관련 DB, 할당·상담·재콜 이력, 미확정 업로드 결과를 트랜잭션 안에서 삭제한다.
- 전역 기본 현장이면 생성 순서가 가장 빠른 남은 현장으로 바꾸고 이력을 남긴다. 남은 현장이 없으면 null로 둔다.
- 현재 화면·미전송 대기열의 삭제된 현장 데이터는 다른 현장으로 전송하지 않는다.
- 앱에서 복구 기능을 제공하지 않는 영구 삭제다. 백업 보관 기간 중 운영 복원 가능성이 있다는 사실은 운영 문서에 별도로 명시한다.

### 7.7 사용자 관리

- 그리드: 이름 / 전화번호 / 비활성화 체크 / 관리자 체크 / 비밀번호 재설정 버튼.
- 비밀번호 원문·해시는 화면/API 응답에 포함하지 않는다.
- 이름·전화번호·역할·활성 상태 편집 후 `저장` → `수정을 반영하시겠습니까?` 확인.
- 추가 모달: 이름·전화번호·관리자 체크. 생성 기본 활성 상태, 초기 비밀번호 `dodream`, 첫 로그인 변경 필수.
- 로그인 ID는 사용자 전화번호로 한다. 이는 별도 ID가 없던 요구사항을 구체화한 구현 기본값이다.
- 사용자 전화번호도 010 형식으로 정규화하며 모든 사용자 사이에서 unique이다. 사용자와 고객의 연락처는 별개 제약이다.
- 재설정은 `dodream`으로 변경하고 비밀번호 변경 필수 상태로 전환한다. 해당 사용자의 기존 세션을 무효화한다.
- 비활성화는 기존 세션을 즉시 무효화하고, 모든 현장의 현재 담당 DB 중 현재 할당 이후 미진행인 DB를 회수한다. 날짜 제한 없음.
- 진행 DB는 담당자를 유지하고 관리자 이관 필요 목록에 표시한다. 재활성화해도 회수 DB를 자동 재배정하지 않는다.
- 직원이 관리자로 바뀌는 경우, 본인 담당 DB와 일정은 유지하되 새 분배 대상에서는 제외한다. 기존 DB 처리는 관리자 화면에서 한다.

### 7.8 고객정보 삭제 요청 알림·승인

관리자 메인 대시보드 상단에 `고객정보 삭제 요청 n건` 알림 영역을 둔다. 모든 관리자가 공유하며 현재 선택 현장과 관계없이 **전체 현장의 미처리 요청**을 보여준다. 같은 요청을 관리자 수만큼 복제하지 않는다.

- 목록 열: 현장명 / 고객명 / 연락처 / 요청 직원 / 요청 시각 / `승인` 버튼.
- 최초 진입·화면 복귀·수동 새로고침 때 조회한다. 대시보드가 보이는 동안에만 기본 60초마다 알림 건수와 목록 첫 페이지를 한 번의 경량 요청으로 갱신한다. 숨겨진 탭·다른 화면에서는 폴링하지 않는다.
- 별도 WebSocket·외부 메시지·이메일·OS 푸시는 초기 범위에서 추가하지 않는다. 정상 온라인·활성 대시보드에서 요청은 다음 조회 시 표시된다.
- 알림은 최신 요청 순으로 서버 페이지 조회한다. 알림을 열거나 읽어도 요청이 처리되지는 않는다.
- 각 요청에 `승인` 버튼을 둔다. 클릭 시 `<고객명> 고객정보를 휴지통으로 이동하시겠습니까?` 확인 후 한 건씩 처리한다. 일괄 승인·반려·직원 취소 기능은 이번 범위에 추가하지 않는다.
- 모든 관리자가 승인할 수 있다. 요청 직원이 비활성화되거나 담당자가 회수·변경되어도 이미 접수된 요청은 유지되며 승인할 수 있다.

승인은 다음을 **하나의 트랜잭션**으로 수행한다.

1. 요청이 PENDING이고 고객정보가 존재하며 아직 삭제되지 않았는지 확인한다.
2. 고객의 최신 `상담기타내용(notes)` 끝에 줄바꿈 후 `[YYYY-MM-DD HH:mm] 고객요청으로 인한 삭제`를 추가한다. 시각은 한국 시간의 실제 승인·삭제 시각이다.
3. `deleted_at`·`deleted_by`를 승인 시각·관리자로 설정하고 현재 할당을 종료한다. 기존 상담정보·재콜·할당 이력은 유지한다.
4. 고객 버전을 증가시키고 요청을 APPROVED로 변경한다. 승인자·승인 시각을 기록한다.
5. 미처리 알림에서 제거하고 해당 DB를 일반·직원 목록에서 제외한다. 휴지통에는 추가한 문구와 함께 표시한다.

여기서 사용자가 말한 `비고`는 기존 **상담기타내용**을 의미하는 것으로 해석한다. 별도 업무 열을 추가하거나 엑셀의 9열 순서를 바꾸지 않는다. UI에서 `상담기타내용(비고)`로 표시할 수 있다. 기존 내용은 덮어쓰거나 자르지 않는다. 사용자 입력 10,000자 제한 때문에 승인 시스템 문구 추가가 실패하지 않도록, 서버는 시스템 추가분을 별도 길이 여유로 허용한다. 복구 후에는 최소 기존 전체 길이까지 편집 가능하게 하되 신규 입력의 기본 제한은 유지한다.

- 두 관리자가 동시에 승인하거나 응답 유실로 재시도해도 최초 승인 시각·승인자를 유지하고 문구·할당 종료를 한 번만 적용한다. 이미 APPROVED이면 기존 결과를 반환한다.
- 요청 중인 고객을 관리자가 일반 삭제로 휴지통에 옮기면 요청은 CLOSED, 사유 ALREADY_DELETED로 종료한다. 고객요청 승인과 구분하며 승인 문구를 자동 추가하지 않는다.
- 고객 또는 현장 영구 삭제 시 연결된 요청도 삭제하고 대시보드에서 제거한다.
- 휴지통 복구 후 과거 승인 이력과 문구는 유지한다. 과거 요청을 재활성화하지 않고, 직원이 필요하면 새로운 요청을 생성할 수 있다.

## 8. 직원 화면

### 8.1 메인 대시보드

- 상단 현장 선택. 최초는 전역 기본 현장.
- 오늘 할당받은 DB 수: 선택 현장에서 오늘 할당 이력의 고유 DB 수.
- 오늘 재콜할 DB 수: 선택 현장·현재 본인 담당·삭제 아님·미완료 일정 중 오늘 또는 과거 예정인 고유 DB 수.
- 오늘 신규 할당 현재 보유 수, 기한 지난 재콜 수를 보조 표시한다.
- 비밀번호 변경 버튼.
- 최초 로그인·재설정 후 비밀번호 변경이 필수이면 다른 업무 화면/API를 사용할 수 없다.
- `오늘 AI 사용 n/30회 · 남은 횟수 m회`를 표시한다. 처리 중 예약 횟수는 별도 표시하고 서버가 확정한 실행 가능 횟수를 사용한다.

### 8.2 오늘의 DB

기본 조회 조건:

```text
선택 현장
AND 삭제되지 않음
AND 현재 담당자 = 로그인 직원
AND (
    현재 할당일이 한국 시간 오늘
    OR 미완료 재콜의 예정일이 한국 시간 오늘 또는 과거
)
```

- DB 한 건은 한 행으로만 표시한다. 여러 재콜 이력이 있어도 중복 행을 만들지 않는다.
- 기본 정렬: 기한 지난 재콜 → 오늘 재콜 → 오늘 할당, 각 그룹 내 재콜 시각·할당 시각·ID 순.
- 할당일 `MM/DD`, 위 9개 업무 열, 재콜 완료 버튼, 행 저장 상태 표시.
- 담당자·고객명·연락처·할당일은 읽기 전용.
- 상담 관련 열은 11장의 자동 저장 적용.
- 우클릭·복사 제한 적용.
- 각 행 작업 영역에 `AI 상담 정리`, `상담 요약`, `다음 질문 제안`을 제공한다. 버튼 클릭만으로 AI 요청을 생성하며 19장의 세 기능 합산 한도를 적용한다. 업무 열 및 엑셀 열에는 포함하지 않는다.

### 8.3 나의 DB

- 선택 현장의 삭제되지 않은 현재 본인 담당 DB 전체.
- 편집·저장·재콜 완료·복사 제한은 오늘의 DB와 동일하다.
- 직원 AI 세 버튼과 일일 한도도 오늘의 DB와 동일하다. 게시된 현장 상담 가이드는 별도 읽기 화면에서 확인할 수 있다.
- 과거 담당 이력만 있고 현재 담당자가 바뀐 DB는 조회 불가.

### 8.4 복사·우클릭 제한

- 직원 고객정보 그리드 영역의 `contextmenu`, `copy`, `cut` 기본 동작을 차단한다.
- Ctrl/Cmd+C, Ctrl/Cmd+X도 같은 영역에서 제한한다. 상담 입력을 위한 붙여넣기는 허용한다.
- 그리드 텍스트 선택을 제한하되 셀 편집 자체와 입력 커서 이동은 가능해야 한다.
- Tabulator의 클립보드·다운로드 기능은 활성화하지 않는다.
- 관리자 화면에는 복사 제한을 적용하지 않는다.
- 이 기능은 브라우저 조작 억제이며 화면 캡처·개발자 도구 등을 통한 완전한 복제 차단을 보장하지 않는다. DLP 기능으로 설명하지 않는다.

### 8.5 직원의 행별 고객정보 삭제 요청

- `오늘의 DB`, `나의 DB` 각각의 고객 행 끝에 `삭제 요청` 버튼을 둔다. 선택 체크박스·선택 행 삭제 요청·일괄 요청 기능은 제공하지 않는다.
- 한 번의 요청은 반드시 고객 한 건만 대상으로 한다. 다른 행들도 각각 요청할 수 있으며 화면 전체에서 동시에 진행 중인 제출은 한 건으로 제한한다.
- 클릭하면 해당 행의 편집을 확정하고 미전송 변경을 먼저 저장한다. 저장 실패·충돌·담당자 변경 시 요청을 제출하지 않고 해결 방법을 안내한다. 다른 행의 100초 저장 타이머는 유지한다.
- 요청 전 확인 문구: `이 고객정보의 삭제를 요청하시겠습니까? 관리자 승인 후 휴지통으로 이동합니다.`
- 전송 중에는 중복 클릭을 막고 `요청 중`으로 표시한다. 서버 성공 응답 후 버튼을 정확히 `요청완료`로 변경하고 비활성화한다.
- 전송 실패 시 `요청완료`로 표시하지 않는다. 같은 요청 키로 재시도할 수 있게 한다.
- 고객당 PENDING 요청은 최대 하나다. 재조회·새로고침·다른 탭에서도 PENDING이면 `요청완료`로 표시한다. 재분배된 새 담당자에게도 같은 상태를 표시한다.
- 요청만으로 DB를 삭제하거나 숨기지 않는다. 관리자 승인 전에는 기존 조회·상담 수정 규칙을 유지한다. 상담 저장과 승인 경합은 기존 행 버전·할당 검사로 처리한다.
- 승인되어 삭제된 행은 다음 조회 또는 저장·요청 응답에서 삭제 사실을 확인했을 때 제거한다. 무효해진 대기열은 `삭제되어 저장 불가`로 표시하며 자동 재등록하지 않는다.
- 삭제 요청 버튼은 시스템 작업 열이며 9개 업무 열 및 엑셀 템플릿에 포함하지 않는다.
- 요청은 현재 본인 담당·삭제되지 않은 고객만 제출 가능하다. 직원은 직접 휴지통 이동 API를 호출할 수 없다.

## 9. 할당·진행·회수의 상태 모델

### 9.1 할당 식별자

고객 ID와 별도로 매 할당마다 새로운 `assignment_id`를 만든다. 모든 직원 저장 요청은 고객 ID, 현재 할당 ID, 행 버전을 함께 보낸다.

- A에게 배정 → 회수 → 다시 A에게 배정되어도 이전 할당 ID로는 저장 불가.
- 담당직원 직접 변경도 재분배이며 새 할당 ID와 현재 할당 시각을 생성한다.
- 담당자를 같은 직원으로 다시 선택한 것은 no-op이다. 할당일과 진행 기준을 초기화하지 않는다.
- 빈 담당자 선택은 회수. 상담정보는 유지하고 현재 할당 연결을 제거한다.
- 할당 종료 시 이력에 종료 시각·사유를 기록한다. 현재 담당자와 할당 시각은 연결된 활성 할당에서 도출한다.

### 9.2 진행 판정 대상

진행을 발생시키는 값: `call_result`, `visit_at`, `contract_status`, `notes`, `housing_status`, 재콜 생성·시각 변경·취소·완료.

진행에 포함하지 않는 작업: 목록 조회, 검색, 필터, 값 변경 없는 저장, 담당자 변경, 할당 시각 갱신, 삭제·복구 자체, 삭제 요청의 접수·상태 변경, 시스템의 일반 `updated_at` 변경.

AI 요청·결과 생성·요약 조회·질문 조회·코칭 및 브리핑 생성은 진행에 포함하지 않는다. 직원이 AI 추천을 선택 적용해 실제 상담 값 변경을 서버에 저장하면 해당 변경은 일반 상담 수정과 동일하게 진행으로 기록한다.

삭제 요청은 상담 값 변경과 구분한다. 요청만 제출한 미진행 DB는 기존 23시·비활성화 회수 규칙을 그대로 따른다. 회수되어도 PENDING 요청은 유지되고 관리자는 승인할 수 있다. 요청 전 실제 상담 변경을 저장했다면 그 상담 변경은 기존 규칙에 따라 진행으로 기록한다.

- 현재 할당 이후 실제 상담 값 변경을 저장할 때 `first_activity_at`을 최초 1회 기록한다.
- 관리자·직원 수정 모두 포함한다.
- 서버에 저장한 후 원래 값으로 되돌려도 `first_activity_at`을 지우지 않는다.
- 저장 전 브라우저에서만 바꿨다가 원복해 서버 변경이 없으면 진행으로 보지 않는다.
- 새 할당의 `first_activity_at`은 null이다. 이전 할당의 진행 이력은 유지하지만 새 할당을 진행으로 만들지 않는다.
- 상담정보를 가져온 업로드는 미할당 상태이므로 이후 할당의 진행 이력으로 취급하지 않는다.

### 9.3 분배의 트랜잭션

- 소규모 초기 구현에서는 업무 쓰기 트랜잭션 시작 시 공통 PostgreSQL transaction-level advisory lock을 획득한다. 예: 고정 bigint 키 `7420192701`. 분배·회수·상담 저장·사용자 상태 변경·현장 설정·삭제·삭제 요청 접수·승인·업로드 확정·예약 회수가 모두 같은 잠금을 사용한다. API 읽기와 업로드 파일 파싱은 이 잠금을 사용하지 않는다.
- 잠금 순서는 공통 advisory lock → 필요한 사용자 ID 정렬 → 전역 설정 → 현장 ID 정렬 → 고객 ID 정렬 → 할당·재콜이다. 대상 조건은 잠금 안에서 재조회한다. 같은 트랜잭션 안의 중첩 서비스 호출도 이 순서를 지킨다.
- 이 방식은 쓰기를 짧게 직렬화해 직원 비활성화와 분배 등 현장 간 경합도 단순하게 해결하는 구현 기본값이다. 1만 행 업로드는 잠금 전에 파일 검증을 끝내고 잠금 안에서는 재검증·bulk insert만 한다. 성능을 측정하고 병목이 확인될 때만 더 세밀한 잠금으로 변경한다.
- 후보 수 재검증, 랜덤 후보 선정, 할당 생성, 현재 할당 연결, 행 버전 증가, 요청 결과 저장을 같은 트랜잭션으로 처리한다.
- 필요한 수량이 없으면 전체 취소한다. 부분 분배 금지.
- 잠금 대기·데드락은 제한된 재시도 후 사용자에게 재시도 메시지를 표시한다. 무한 재시도 금지.
- 분배·회수·업로드 확정·영구 삭제·삭제 요청 접수·승인에는 요청별 idempotency key를 적용한다. 동일 키·동일 본문이면 기존 결과를 반환하고, 동일 키·다른 본문은 거부한다.

### 9.4 23시 자동 회수

일일 기준 날짜 D, 한국 시간 D일 23:00을 cutoff로 한다.

대상 조건:

```text
cutoff 시점의 전역 기본 현장
AND 삭제되지 않음
AND 현재 할당이 존재함
AND 현재 할당 시각이 D일 00:00 이상, cutoff 이하
AND 현재 할당의 first_activity_at IS NULL
```

- **통화결과의 null 여부만으로 회수하지 않는다.** 한 상담 값이라도 실제 저장했다면 제외한다.
- 현재 할당이 미진행이면 기존 재콜·방문예약 값이 있다는 이유만으로 제외하지 않는다. 마지막 승인 규칙의 진행 이력 기준을 따른다.
- 담당자·현재 할당을 해제하며 상담정보와 재콜 일정은 유지한다. 미할당 DB는 직원 재콜 조회에 나오지 않는다.
- 서버에 커밋된 변경만 인정한다. 브라우저 미전송 자료는 회수 제외 근거가 아니다.
- 직원 클라이언트는 22:59:30 전후에 열린 편집을 확정하고 대기열 즉시 전송을 시도한다. 백그라운드 탭·오프라인의 전송 성공은 보장하지 않는다.
- 서버가 먼저 저장을 커밋하면 진행으로 남고, 회수가 먼저 커밋되면 뒤늦은 저장은 거부한다. 클라이언트 시각으로 순서를 조작하지 않는다.
- cutoff 이후 새로 배정한 DB는 그날 자동 회수에 포함하지 않는다.
- 예약 실행이 늦어져도 D일과 cutoff를 보존한다. 실행 당시 날짜를 `오늘`로 다시 계산하지 않는다.
- 지연 실행 시 이미 재할당되었거나 그 사이 상담 변경이 저장된 현재 할당은 회수하지 않는다. 지연 작업이 정상 업무를 되돌리지 않게 한다.
- 전역 기본 현장 변경 이력으로 cutoff 시점의 현장 ID를 결정한다. 재시도 중 새 기본 현장으로 바꾸지 않는다.
- `ScheduledJobRun`에 `(job_type, business_date)` 유일 제약을 둔다. 실행·실패·재시도·완료·회수 건수 기록.
- 현장이 없거나 삭제되었다면 0건 완료로 기록한다.
- 예약 작업은 브라우저와 무관하게 서버에서 실행한다. 서버 재시작 후 운영 시작일부터의 누락·실패 작업을 확인하고 재실행한다.
- 같은 날짜 작업을 여러 번 실행해도 중복 할당 종료나 이력이 생기지 않아야 한다.

## 10. 재콜 일정

- 재콜은 별도 엔터티로 관리하며 고객당 미완료 일정은 최대 하나다.
- 그리드에는 미완료 일정의 시각을 표시한다. 완료 이력은 상세 모달에서 조회한다.
- 새 날짜 입력: 미완료 일정 생성. 이미 있으면 기존 일정의 시각을 수정한다.
- 날짜를 비우면 기존 미완료 일정을 `CANCELLED`로 종료한다. 이력은 유지한다.
- `재콜 완료` 클릭 시 해당 일정 ID·버전·현재 할당 ID를 전송해 `COMPLETED`로 변경한다.
- 완료하면 현재 일정 셀을 비우고 미처리 목록에서 제외한다. 완료 시각·처리자를 기록한다.
- 재콜 완료 전에 해당 행의 미저장 변경을 먼저 저장한다. 완료 동작은 즉시 요청이며 100초 대기 대상이 아니다.
- 이후 새 일정을 등록할 수 있다. 완료 요청 재시도가 새 일정을 완료시키면 안 된다.
- 재분배해도 미완료 일정은 고객에게 남고 새 담당자의 조회 대상이 된다.
- 오늘 이전에 예정된 미완료 재콜을 포함한다. 시각이 아직 오지 않은 오늘 일정도 오늘의 DB에 표시한다.

## 11. 직원 자동 저장·IndexedDB·충돌 처리

### 11.1 저장 시점

1. 셀 편집 완료 시 입력값을 검증한다.
2. 변경 값을 로컬 대기열에 합치고 IndexedDB에 기록한다.
3. 첫 미전송 변경 후 90초를 목표 전송 시점으로 설정해 정상 온라인·활성 화면에서 100초 이내 요청을 시작한다.
4. 추가 입력으로 최초 타이머를 늦추지 않는다. 수정이 없으면 저장 API를 호출하지 않는다.
5. 같은 고객·필드의 미전송 변경은 마지막 값으로 합친다. 원복한 미전송 값은 제거한다.
6. 한 요청에서 여러 행의 변경 필드만 전송한다. 기본 최대 100행/요청으로 분할한다.
7. 페이지·검색·필터·현장·화면 이동·명시적 로그아웃 시 현재 편집을 확정한 뒤 즉시 저장한다.
8. `지금 저장` 버튼을 제공해 사용자가 즉시 저장할 수 있게 한다.

100초는 서버 장애·오프라인·브라우저 정지 시 성공 보장이 아니다. 예약 타이머가 백그라운드에서 지연될 수 있으므로 화면 복귀·온라인 복구 시 만료 대기열을 즉시 전송한다. 업무 시간 밖에도 같은 저장 규칙을 적용한다.

### 11.2 저장 상태

`저장 완료`, `미저장 n건`, `저장 중`, `오프라인·임시 보관`, `저장 실패·재시도`, `충돌·확인 필요`, `회수/삭제되어 저장 불가`를 구분한다. 실패한 값을 성공으로 표시하지 않는다.

### 11.3 대기열 식별과 수명

- IndexedDB 키에 로그인 사용자 ID, 현장 ID, 고객 ID, 할당 ID를 포함한다.
- 전체 DB·세션 토큰·비밀번호를 저장하지 않는다. 미전송 변경값과 저장에 필요한 식별자·기준 버전만 보관한다.
- 서버 확인 전에는 대기열을 제거하지 않는다.
- 로그아웃 전 전송 실패 시 `재시도 / 로그아웃 취소 / 변경 폐기 후 로그아웃`을 제시한다. 변경 폐기는 명시적 확인을 받는다.
- 브라우저 강제 종료 시 이미 기록된 대기열은 다음 동일 계정 로그인 후 검증·복구한다. 다른 계정은 대기열을 열람·전송할 수 없다.
- 재로그인 시 현재 담당자·할당·권한·삭제 여부를 서버에서 검증한 후 복구한다. 오래된 요청을 무조건 재전송하지 않는다.
- 브라우저 저장소 용량 오류가 발생하면 임시 저장 실패를 표시하고 즉시 서버 전송을 시도한다. 서버도 실패하면 화면 이탈을 안내한다.
- 브라우저 종료 이벤트의 네트워크 요청에만 의존하지 않는다.

### 11.4 전송 중 추가 수정

- 요청에 포함한 대기열 스냅샷과 이후 새로 입력한 변경을 분리한다.
- 응답 성공 시 그 요청에서 확인된 변경만 제거한다. 전송 중 새로 입력한 값을 삭제하지 않는다.
- 성공 응답의 새 버전을 이후 대기열 기준에 반영한다.
- 같은 행의 네트워크 저장은 직렬화한다. 여러 탭의 요청은 서버 행 버전으로 충돌 감지한다.

### 11.5 중복·충돌

- 각 행 변경 요청은 고유 `mutation_id`, `expected_version`, 직원 요청의 `assignment_id`를 포함한다.
- 서버는 현재 로그인·권한·담당자·할당 ID·삭제 여부·행 버전을 검사한다.
- 같은 mutation의 재시도는 동일 결과를 반환한다. 응답 유실 후 재시도해도 저장·진행 이력을 중복 생성하지 않는다.
- 다른 관리자의 변경·다른 탭의 변경으로 버전이 다르면 `VERSION_CONFLICT`를 반환한다. 서버 최신값과 내 변경값을 보여주고 재적용·폐기를 선택하게 한다. 조용한 덮어쓰기 금지.
- 회수·재분배는 `ASSIGNMENT_CHANGED`, 삭제는 `CUSTOMER_DELETED`로 거부한다. 이전 할당 ID를 새 할당 ID로 자동 교체해 저장하지 않는다.
- 직원 세션 만료·비활성화·비밀번호 변경 요구는 각각 별도 오류로 표시한다. 인증 실패를 무한 재시도하지 않는다.
- 배치 저장은 **행 단위 원자성**이다. 유효한 행은 성공하고 충돌한 행만 보류한다. 한 행의 일부 필드만 저장하지 않는다.
- 일시 오류는 2·5·15·30·60초 간격을 상한으로 재시도하고 약간의 무작위 지연을 둔다. 오프라인이면 온라인 복구 이벤트를 기다린다.
- 일반 화면 이동은 저장 성공 후 진행한다. 사용자가 명시적으로 변경 폐기를 선택하면 해당 대기열을 제거하고 이동한다.

## 12. 엑셀 업로드

### 12.1 형식

- `.xlsx`, 파일당 최대 10MB·데이터 10,000행. 용량은 구현 기본값.
- 첫 워크시트만 사용하고 첫 행은 헤더이다. 숨겨진 다른 시트는 처리하지 않는다.
- 9개 업무 열을 6.1 순서로 매핑한다. 헤더 이름·순서 불일치 시 파일 전체 검증 실패로 안내한다. 열을 임의 추측하지 않는다.
- 입력 양식을 내려받을 수 있게 한다. 이는 관리자용 빈 템플릿이며 고객 데이터 내보내기가 아니다.
- 할당일·체크박스·재콜 완료·저장 상태 등 시스템 열은 템플릿에 없다.
- 담당직원명 열은 빈 값이어야 한다. 값이 있으면 그 행을 실패 처리한다.
- 고객명·연락처만 필수. 나머지 열은 비어 있어도 된다.
- 통화결과·계약여부는 허용값 검증. 빈 계약여부는 `미확인`.
- 방문예약·재콜은 Excel datetime 또는 `YYYY-MM-DD HH:mm`, 표시용 `(요일)`이 포함된 같은 날짜·시각 형태를 허용한다. 요일은 날짜에서 재계산한다. 날짜만 있고 시각이 없으면 행 오류로 안내한다.
- 전화번호가 숫자로 입력되어 앞자리 0이 소실된 값은 임의 복원하지 않고 오류로 안내한다. 템플릿 연락처 열은 텍스트 서식을 사용한다.
- 수식 셀·매크로 파일은 허용하지 않는다. 날짜·숫자 형식을 자의적으로 실행·평가하지 않는다.
- 빈 행은 건수에서 제외하고 오류는 원본 Excel 행 번호로 표시한다.

### 12.2 검증·확정

1. 현장 선택 → 파일 선택 → 서버 검증.
2. 총 데이터 수, 등록 가능 수, 파일 내 중복, 기존 중복, 형식 오류 표시.
3. 사용자가 업로드 확정 → 같은 현장·현재 디비 상태로 재검증 → 정상 행 저장.
4. 검증 때 통과해도 다른 업로드로 중복이 생기면 확정 결과에서는 실패로 처리한다.
5. 같은 파일 안에서는 첫 번째 **유효한** 연락처 행만 후보로 인정한다. 앞선 행이 형식 오류면 뒤의 유효 행을 허용한다.
6. 기존 연락처는 휴지통도 포함해 중복 처리한다. 기존 상담내용을 덮어쓰지 않는다.
7. 행 오류는 해당 행만 실패. 정상 행은 저장하되 치명적인 디비 오류가 나면 업로드 확정 전체를 롤백한다.
8. 확정 요청은 idempotency key로 중복 저장 방지. 재시도 결과의 성공 건수가 바뀌지 않아야 한다.

성공 안내:

> 엑셀 1,000개 데이터 중 920개 업로드를 성공했습니다. 80개는 업로드를 실패했습니다. 실패 목록을 확인해 주세요.

- 실패 목록: 행 번호·고객명·마스킹하지 않은 관리자용 연락처·오류 코드·사유. 실패 원문은 서버 로그에 남기지 않는다.
- 원본 파일은 검증 후 삭제한다. 검증 결과와 유효 후보는 서버에 24시간 임시 보관 후 정리한다. 확정 후 후보 원문은 제거한다.
- 파일 없이도 사용자가 실패 사유를 확인할 수 있도록 결과 화면을 제공한다. 결과 메타데이터의 정리 기준도 운영 문서에 명시한다.
- 현장 삭제·검증 결과 만료 후 확정은 거부한다.

## 13. 디비 논리 설계

모든 변경 가능한 엔터티에 생성·수정 시각을 둔다. 날짜는 `timestamptz`, 고유 식별자는 UUID를 기본으로 한다. 실제 마이그레이션에서 필드명·역참조·제약 이름을 명시한다.

### 13.1 User

| 필드 | 규칙 |
|---|---|
| id | UUID PK |
| name | 필수 |
| phone_normalized | 로그인 ID, unique |
| role | ADMIN / EMPLOYEE |
| is_active | boolean, 기본 true |
| password | Django 해시만 저장 |
| must_change_password | 신규·재설정 true |
| session_version | 비밀번호 재설정·비활성화·중요 권한 변경 시 증가 |

UI의 관리자 체크는 role로, 비활성화 체크는 `not is_active`로 매핑한다. 원래의 `관리자=null·비활성화=null` 의미는 `role=EMPLOYEE AND is_active=true`로 구현한다.

### 13.2 Site / GlobalSettings / DefaultSiteHistory

- Site: `id`, `name`, `name_key(unique)`, 생성자·생성 시각.
- GlobalSettings: 한 행, `default_site_id(nullable)`, `version`.
- DefaultSiteHistory: 이전/새 현장 ID, 변경 시각, 처리자. 삭제된 현장의 식별 이력은 nullable 참조와 ID 스냅샷으로 보존해 cutoff 해석을 가능하게 한다.
- 설정 변경과 이력 기록은 한 트랜잭션이다.

### 13.3 Customer

- `id`, `site_id`, `customer_name`, `phone_normalized`.
- `call_result(nullable)`, `visit_at(nullable)`, `contract_status`, `notes`, `housing_status`.
- `current_assignment_id(nullable)`, `deleted_at(nullable)`, `deleted_by(nullable)`.
- `version`: 실제 업무 변경·할당 변경·삭제·복구마다 증가하는 정수.
- `import_batch_id(nullable)`, `created_at`, `updated_at`.
- unique: `(site_id, phone_normalized)`, 휴지통 포함.
- 고객명·연락처는 등록 서비스에서만 설정하고 일반 update 서비스에서 금지한다.

### 13.4 Assignment

- `id`, `customer_id`, `employee_id`, `assigned_at`, `assigned_by`.
- `first_activity_at(nullable)`.
- `ended_at(nullable)`, `end_reason(nullable)`, `ended_by(nullable)`.
- 종료 사유: MANUAL_RECALL / AUTO_RECALL / REASSIGNED / USER_DISABLED / SOFT_DELETED.
- 고객당 `ended_at IS NULL`인 할당 최대 하나라는 부분 유일 제약.
- `current_assignment_id`가 가리키는 할당의 고객 일치·미종료 상태는 도메인 서비스와 테스트로 보장한다. 참조 갱신과 할당 종료를 같은 트랜잭션으로 처리한다.
- 고객을 영구 삭제할 때 순환 참조를 먼저 해제한 후 관련 할당을 삭제한다.

### 13.5 Callback

- `id`, `customer_id`, `due_at`, `status(PENDING/COMPLETED/CANCELLED)`.
- 생성·수정·완료 처리자, 완료/취소 시각, `version`.
- 고객당 PENDING 하나라는 부분 유일 제약.
- 원래 고객 담당자를 별도 복사해 소유자로 사용하지 않는다. 접근 권한은 고객의 현재 할당 기준이다.

### 13.6 CustomerChangeEvent

- 고객·할당·변경자·변경 시각·변경 필드 목록.
- 진행 판정 이력을 보존한다. v2.0부터 상담 본문·항목의 실제 변경은 19.6의 ConsultationRevision에도 기록한다. 기존의 원문 미보관 원칙은 AI 분석용 상담 이력에 한해 변경한다.
- 미할당 상태의 관리자 상담 수정은 customer 이력만 남긴다. 이후 새 할당의 진행으로 소급하지 않는다.
- 고객 영구 삭제 시 연결 이력도 삭제한다.

### 13.7 ImportBatch / ImportCandidate / ImportRowResult

- 업로드 현장·처리자·상태·만료 시각·총/성공/실패 건수.
- 후보·행 결과는 원본 행 번호와 정규화 값·오류 코드를 보관한다.
- 확정 상태 전이는 VALIDATED → COMMITTED 또는 EXPIRED.
- 확정 중 치명 오류는 FAILED로 기록하고 고객 생성은 롤백한다. 재시도 정책을 명시한다.

### 13.8 IdempotencyRecord / MutationReceipt

- 처리자·작업 종류·요청 key·본문 해시·최종 결과·대상 ID 목록.
- 같은 키 재사용과 본문 불일치를 검사한다.
- 영구 삭제 요청 이외의 응답에 포함된 고객 내용은 고객·현장 영구 삭제 시 함께 제거한다. 재시도 기록에 삭제 정보가 남지 않게 한다.
- 구현 기본 보관 7일. 클라이언트는 보관 기간을 지난 미확인 요청을 자동 재실행하지 않고 서버 상태 재검증을 요구한다.
- 데이터 변경과 receipt 작성은 원자적으로 커밋한다.

### 13.9 ScheduledJobRun / OperationEvent

- ScheduledJobRun: 작업 종류·기준 날짜·cutoff·대상 현장 ID·상태·시도 횟수·실행 시각·건수·오류 코드.
- unique: `(job_type, business_date)`.
- OperationEvent: 사용자 관리·기본 현장 변경·분배·회수·삭제 요청·승인·영구 삭제의 처리자·시각·종류·건수. 비밀번호·고객 원문을 포함하지 않는다.

### 13.10 인덱스

- Customer: `(site_id, phone_normalized)` unique, `(site_id, deleted_at, created_at, id)`.
- Assignment: `(employee_id, ended_at, assigned_at)`, `(assigned_at, employee_id)`, 고객별 미종료 unique.
- Callback: 고객별 PENDING unique, PENDING 대상 `(due_at, customer_id)`.
- Customer current_assignment 참조·모든 외래키 기본 인덱스.
- 무분별한 모든 열 인덱스는 피한다. 고객명 부분검색이 병목이면 측정 후 `pg_trgm` 등을 검토한다.
- 직원 조회·집계에서 N+1 쿼리를 방지한다.

### 13.11 CustomerDeletionRequest

| 필드 | 규칙 |
|---|---|
| id | UUID PK |
| customer_id | Customer FK, 고객 또는 현장 영구 삭제 시 CASCADE |
| requested_by_id | 요청 직원 FK, 직원 비활성화 후에도 유지 |
| requested_assignment_id | 요청 당시 Assignment FK, 이력용이며 승인 시 현재 담당자 일치를 요구하지 않음 |
| requested_at | 서버 접수 시각 |
| status | PENDING / APPROVED / CLOSED |
| approved_by_id / approved_at | 승인 관리자·실제 삭제 시각, PENDING이면 null |
| closed_at / close_reason | 다른 경로로 삭제되어 요청을 종료한 시각·사유 |
| deletion_note | 실제 추가한 고정 삭제 문구, 중복 처리 확인용이며 클라이언트 자유 입력 불가 |

- 고객당 `status=PENDING`인 요청 최대 하나라는 부분 유일 제약을 둔다. 신규 idempotency key로 중복 요청하더라도 기존 PENDING 요청을 반환한다.
- 알림용 `(status, requested_at, id)` 인덱스를 둔다. 관리자별 알림 엔터티는 추가하지 않는다.
- 고객 목록에 `pending_deletion_request_id`와 `deletion_request_status`를 함께 응답해 행별 별도 조회 API가 필요하지 않게 한다.
- 요청 접수 자체는 고객의 상담 버전·first_activity_at을 변경하지 않는다. 접수 시 로그인 직원·현재 할당 ID·삭제 여부는 잠금 안에서 재확인한다.
- 승인 시에는 오래된 notes 스냅샷을 쓰지 않고 잠금 안에서 읽은 최신 notes에 추가한다. 요청 상태 전환·내용 추가·휴지통 이동·할당 종료·요청 영수증 저장은 모두 원자적으로 커밋한다.
- 고객 영구 삭제는 이 요청 및 응답 캐시의 고객 원문도 함께 제거한다.

### 14.2 목록 쿼리

```text
site_id=UUID
view=all|today|mine|trash
q=검색어
page=1
page_size=50
sort=허용된필드
filters=검증된 구조의 JSON
```

- `all`, `trash`는 관리자만 사용한다.
- 클라이언트의 임의 ORM lookup·SQL·열 이름은 받지 않는다. 정렬·필터 허용 목록을 둔다.
- 재콜·할당 조인으로 중복 행이 발생하지 않게 한다.

### 14.3 저장 요청 예시

```json
{
  "rows": [
    {
      "customer_id": "uuid",
      "assignment_id": "uuid",
      "mutation_id": "uuid",
      "expected_version": 12,
      "changes": {
        "call_result": "INTERESTED",
        "notes": "방문 일정은 추후 협의",
        "housing_status": "전세"
      }
    }
  ]
}
```

- 내부 enum과 한글 표시값 매핑은 서버와 클라이언트가 공유한다. enum: NO_ANSWER, REJECTED, INTERESTED, CALL_AGAIN, VISIT_BOOKED, VISITED, REVISITED.
- 직원 assignment_id 필수. 관리자는 조회 시의 assignment_id 또는 null을 보내 담당자 변경 경합도 감지한다.
- 허용하지 않은 변경 필드가 포함되면 행 전체를 거부한다.
- 응답: 행별 성공 여부·mutation_id·새 버전·정규화된 변경 값 또는 오류 코드.

### 14.4 분배 요청 예시

```json
{
  "site_id": "uuid",
  "target": "ALL_EMPLOYEES",
  "per_employee_count": 30,
  "idempotency_key": "uuid"
}
```

개별 대상은 `target=EMPLOYEE`, `employee_id`를 사용한다. 부족 응답에 `available_count`, `employee_count`, `max_per_employee`를 포함한다.

| 코드 | 처리 |

| UNAUTHENTICATED / ACCOUNT_DISABLED | 업무 중지, 로그인 화면 안내 |
| PASSWORD_CHANGE_REQUIRED | 비밀번호 변경 화면으로 이동 |
| FORBIDDEN | 권한 없음 |

## 15. 로그인·비밀번호·세션

- 초기·재설정 비밀번호는 승인대로 `dodream`이다.
- 첫 로그인·재설정 후 반드시 다른 비밀번호로 변경해야 한다. `dodream` 재사용은 거부한다.
- 구현 기본 비밀번호 조건: 8자 이상, 최대 128자, 일반 Django 검증 적용. 원문을 로그에 남기지 않는다.
- 비밀번호 변경 모달: 현재 비밀번호 / 새 비밀번호 / 새 비밀번호 확인. 최초 변경도 현재 비밀번호를 검증한다.
- 로그인 실패 제한은 계정·요청 빈도를 기준으로 적용한다. 접속 가능한 IP 자체를 제한하는 기능과 구분한다.
- 모든 요청에서 사용자 활성 상태와 `session_version`을 확인한다. 웹 서버 메모리 캐시로 비활성 세션을 계속 허용하지 않는다.
- 비활성화·재설정 시 버전 증가로 다른 브라우저의 기존 세션도 차단한다.
- 본인 비밀번호 변경 시 현재 세션은 유지 가능하나 다른 세션은 무효화한다.
- 최초 관리자 생성은 관리 명령으로 수행한다. 코드에 공용 운영 계정을 하드코딩하지 않는다.
- 2단계 인증은 초기 범위에서 제외한다. 초기 추천이 아니라 마지막 승인된 간단한 계정 흐름을 따른다.

## 16. 예약 실행·백업·운영

### 16.1 예약 프로세스

- 같은 앱 이미지의 별도 `scheduler` 프로세스가 30~60초마다 실행할 작업을 확인한다. API 호출 없이 디비와 도메인 서비스를 사용한다.
- 23시 자동 회수와 임시 업로드 정리를 수행한다.
- 디비 고유 실행 키·트랜잭션 잠금으로 중복 프로세스가 있어도 중복 처리하지 않는다.
- SIGTERM·재시작 시 실행 중 작업이 영구 RUNNING에 갇히지 않도록 lease/timeout을 둔다.
- 디비 변경과 작업 완료 기록을 일관되게 커밋한다. 실패한 작업은 상태·재시도 횟수·마지막 오류 코드로 추적한다.
- 백업은 별도 운영 예약 명령으로 실행한다. 백업 실패를 성공으로 표시하지 않는다.

- 23시 작업을 수행해야 하므로 서버를 18시에 자동 종료하지 않는다.
- HTTPS·프록시 헤더·정적 파일·헬스체크를 배포 환경에서 검증한다.
- 현장·고객 영구 삭제는 운영 백업을 즉시 수정하지 않는다. 복원하면 삭제 데이터가 재등장할 수 있으므로 복원 절차에 삭제 작업 확인을 포함한다.

## 18. 필수 검수 기준

### 18.1 권한·계정

- [ ] 직원이 다른 직원의 고객 ID·할당 ID를 보내도 조회·저장이 거부된다.
- [ ] 직원의 필터 후보값에 타인 DB 값이 포함되지 않는다.
- [ ] 관리자도 고객명·연락처 수정 API를 사용할 수 없다.
- [ ] 초기·재설정 비밀번호가 dodream이며 변경 전 업무 API는 차단된다.
- [ ] 비활성화·재설정 후 다른 브라우저의 기존 세션이 다음 요청부터 차단된다.
- [ ] 마지막 활성 관리자를 제거할 수 없다.

### 18.2 현장·업로드

- [ ] 현장 중복 생성의 동시 요청도 하나만 성공한다.
- [ ] 기본 현장 변경은 작업 중인 화면을 강제 전환하지 않고 다음 화면부터 적용된다.
- [ ] 첫 현장·기본 현장 삭제·마지막 현장 삭제의 빈 상태가 정상이다.
- [ ] 고객명·연락처 누락, 잘못된 enum·날짜·담당자 값은 행 오류로 표시된다.
- [ ] 010 하이픈 유무는 동일 연락처로 취급한다. 다른 현장의 같은 번호는 등록된다.
- [ ] 휴지통 중복·파일 내 중복·동시 업로드 중복이 기존 상담정보를 덮어쓰지 않는다.
- [ ] 검증 당시 정상이어도 확정 전에 생긴 중복을 다시 검사한다.
- [ ] 같은 업로드 확정 재시도가 이중 등록되지 않는다.
- [ ] 1만 행 처리의 메모리·응답 시간을 측정하고 시간 초과를 조용히 무시하지 않는다.

### 18.3 분배·수동 회수

- [ ] 직원 4명·잔여 95건·각 30건 요청은 0건 처리되며 23개씩 가능 알림을 표시한다.
- [ ] 관리자 두 명이 동시에 분배해도 같은 DB의 현재 할당은 하나다.
- [ ] 더블클릭·응답 유실·동일 key 재시도에도 분배가 한 번만 실행된다.
- [ ] 분배 중 직원 비활성화와 경합해도 비활성 직원에게 유효한 새 배정이 남지 않는다.
- [ ] 수동 회수는 오늘의 현재 할당 전체를 회수하며 진행 DB도 포함한다. 과거 할당은 제외한다.
- [ ] 회수 후 상담정보·재콜 이력은 유지된다.
- [ ] 동일 직원 재선택은 할당일을 초기화하지 않는다. 다른 직원 선택은 새 할당을 생성한다.

### 18.4 저장·경합

- [ ] 변경이 없는 동안 자동 저장 API를 호출하지 않는다.
- [ ] 정상 온라인·활성 화면에서 연속 입력해도 첫 변경 후 100초 이내 전송을 시작한다.
- [ ] 같은 셀 반복 변경은 마지막 값만 전송한다.
- [ ] 요청 중 새로 입력한 값이 이전 응답으로 삭제되지 않는다.
- [ ] 응답 유실 후 같은 mutation 재시도는 이력·수정을 중복 생성하지 않는다.
- [ ] 한 행의 충돌이 다른 정상 행의 성공을 막지 않는다.
- [ ] 버전 충돌을 조용히 덮어쓰지 않는다.
- [ ] 회수·동일인 재배정 이후 이전 할당의 대기열은 저장되지 않는다.
- [ ] 오프라인·새로고침·브라우저 재시작 후 동일 계정의 대기열을 검증·복구한다.
- [ ] 다른 계정은 이전 계정의 미전송 값을 표시·전송하지 않는다.
- [ ] 저장 실패 중 화면 이동·로그아웃에 명시적 선택을 요구한다.

### 18.5 자동 회수·진행

- [ ] 오늘 23시 이전 현재 할당·미진행·기본 현장 DB만 자동 회수한다.
- [ ] 통화결과가 비어 있어도 상담내용·주택상황 등 실제 저장이 있으면 회수하지 않는다.
- [ ] 저장된 값 원복·관리자 상담 수정도 진행으로 남는다.
- [ ] 저장 전 원복·무변경 저장·조회·필터는 진행으로 만들지 않는다.
- [ ] 과거 할당·다른 현장·23시 이후 새 할당은 회수하지 않는다.
- [ ] 저장과 회수 경합은 커밋 순서에 따라 일관되게 처리한다.
- [ ] 기본 현장이 변경돼도 재시도는 cutoff 시점의 현장을 유지한다.
- [ ] 서버 중단 후 누락 실행·중복 실행이 중복 회수나 새 할당 손상을 일으키지 않는다.
- [ ] 비활성화 회수는 모든 현장·모든 날짜의 현재 미진행 할당에 적용된다.

### 18.6 재콜·삭제·운영

- [ ] 오늘의 DB는 오늘 할당 OR 오늘/과거 미완료 재콜이며 한 고객은 한 행이다.
- [ ] 재콜 완료 후 기한 경과 목록에서 빠지고 이력은 남는다.
- [ ] 완료 요청 재시도가 이후 생성된 새 일정을 완료시키지 않는다.
- [ ] 휴지통 복구는 기존 통화결과를 유지하고 미할당 상태로 복구한다.
- [ ] 개별 영구 삭제 후 같은 번호 재등록이 가능하고 이전 내용·이력은 조회되지 않는다.
- [ ] 현장 삭제 후 관련 조회·미전송 저장·업로드 확정이 안전하게 거부된다.
- [ ] 직원 그리드에서 복사·우클릭·잘라내기는 제한되고 편집·붙여넣기는 가능하다.
- [ ] 직원용 고객정보 다운로드 경로가 없다.
- [ ] 백업을 별도 환경에 실제 복원하고 계정·할당·상담·재콜 정합성을 확인한다.

### 18.7 직원 삭제 요청·관리자 승인

- [ ] 오늘의 DB·나의 DB에 행별 삭제 요청 버튼이 있고 체크박스 일괄 요청은 없다.
- [ ] 한 요청은 고객 한 건만 처리하고 제출 중 추가 클릭을 막는다.
- [ ] 해당 행 미저장 내용의 저장에 실패하면 삭제 요청은 생성하지 않는다.
- [ ] 접수 성공 후 `요청완료`가 표시되고 새로고침·다른 탭에서도 유지된다. 실패를 완료로 표시하지 않는다.
- [ ] 직원이 타인의 고객 ID나 과거 할당 ID로 요청하면 거부된다.
- [ ] 동일 고객의 중복 요청·응답 유실 재시도에 PENDING 요청이 하나만 생긴다.
- [ ] 요청만으로 휴지통 이동·담당자 해제·상담정보 변경이 일어나지 않는다.
- [ ] 모든 관리자 대시보드에 현재 선택 현장과 관계없이 같은 전체 현장 요청이 표시된다.
- [ ] 알림 조회는 활성 대시보드에서만 기본 60초 주기로 수행하며 행마다 API를 호출하지 않는다.
- [ ] 승인 전 고객 상담내용이 바뀌어도 승인 시 최신 내용에 삭제 문구를 덧붙인다.
- [ ] 승인하면 휴지통으로 이동하고 `[한국 시간 승인일시] 고객요청으로 인한 삭제`가 상담기타내용에 추가된다.
- [ ] 빈 비고·10,000자 비고에서도 기존 내용을 훼손하지 않고 승인 문구가 기록된다.
- [ ] 두 관리자 동시 승인·응답 유실 재시도에도 문구·삭제·할당 종료가 한 번만 적용된다.
- [ ] 승인 후 직원 저장은 거부되고 미전송 자료를 성공으로 처리하지 않는다.
- [ ] 요청 후 회수·재분배·직원 비활성화가 있어도 관리자 승인으로 처리할 수 있다.
- [ ] 일반 삭제로 이미 처리된 요청은 CLOSED로 종료되며 별도 승인 문구가 중복 생성되지 않는다.
- [ ] 복구 후 이전 승인은 되돌리지 않고 필요한 경우 새로운 삭제 요청을 할 수 있다.
- [ ] 고객·현장 영구 삭제 시 관련 요청과 알림이 함께 제거된다.

### 18.8 AI 기능·사용 한도·결과 적용

- [ ] 직원의 세 AI 기능은 버튼을 눌렀을 때만 실행되고 합산 하루 30회로 제한된다.
- [ ] 화면 진입·자동 저장·예약 작업·관리자 알림 폴링에서 AI 생성 호출이 발생하지 않는다.
- [ ] 29회 성공 상태에서 여러 탭이 동시에 요청해도 성공+예약 합계가 30회를 넘지 않는다.
- [ ] 동일 요청 키 재시도·결과 재조회·이중 클릭에 호출과 차감이 중복되지 않는다.
- [ ] 확실한 실패는 예약 횟수를 반환하고, 결과 성공 후 응답 유실은 재조회해 동일 결과를 받는다.
- [ ] 외부 처리 여부가 불명확한 timeout을 무조건 새 유료 호출로 재실행하지 않는다.
- [ ] 자정 전 접수·자정 후 완료는 접수일 한도로 계산하며 다른 날짜의 예약을 차감하지 않는다.
- [ ] AI 생성 자체는 진행 이력으로 남지 않고, 선택 적용 후 실제 저장한 값만 진행으로 남는다.
- [ ] AI 처리 중 회수·재분배·삭제·비활성화가 발생하면 직원에게 결과를 노출하거나 적용하지 않는다.
- [ ] AI 요청 시점과 다른 버전의 고객에 추천을 조용히 덮어쓰지 않는다.
- [ ] 없는 날짜·가격·계약 여부를 임의로 생성하지 않으며 불명확한 정보는 확인 필요로 표시한다.
- [ ] 직원이 다른 직원의 AI 결과 ID를 사용해도 조회되지 않는다.
- [ ] 상담기록 안의 지시문을 실행하거나 외부 URL·도구·SQL을 호출하지 않는다.
- [ ] 일요일 이외 주간 브리핑 생성 요청은 서버에서 거부하고 기존 결과 읽기는 허용한다.
- [ ] 주간 범위가 한국 시간 월요일 00:00~일요일 요청 시각이며, 아직 지나지 않은 일요일 업무를 포함했다고 표시하지 않는다.
- [ ] 관리자 동시 요청에서도 같은 주 브리핑, 같은 직원의 당일 코칭, 같은 현장의 당일 가이드가 중복 생성되지 않는다.
- [ ] 코칭은 실제 처리자별 30일 이력과 기존 코칭을 사용하고, 데이터가 없으면 부족함을 표시한다.
- [ ] 상담 메모 반복 저장을 별도 통화 횟수·별도 고객 반응으로 중복 집계하지 않는다.
- [ ] AI 생성 가이드는 검토·게시 전 직원에게 노출되지 않는다.
- [ ] 고객·현장 영구 삭제 시 원문뿐 아니라 관련 AI 입력·출력·비교 코칭·가이드의 파생정보 처리도 검증한다.
- [ ] 키 없음·예산 소진·AI 공급자 장애에도 기본 DB 업무가 계속 동작한다.
- [ ] `.env.ai`는 git check-ignore에 포함되고 .env.ai.example은 제외된다. 실제 키 파일이 Git 추적 대상과 Docker 빌드 컨텍스트에 없다.
- [ ] 실제 키가 브라우저 응답·소스맵·로그·문서·테스트 fixture에 포함되지 않는다.

## 19. AI 기능 통합 상세 설계

### 19.1 사용자 지정 사항과 구현 기본값

**사용자 지정 사항:** 직원에게 상담 정리·항목 추천, 재통화 전 요약, 다음 질문 제안의 세 기능을 제공한다. 각 버튼을 누를 때만 실행하며 직원별 하루 총 30회다. 팀장은 일요일에만 이번 주 월~일 업무 브리핑을 생성한다. 브리핑에는 고객 반응·거절 사유 분석과 상담 기록 검토 보조를 반드시 포함한다. 직원별 코칭은 이전 코칭과 지난 30일의 해당 직원 정보를 분석한다. 팀 공통 상담 가이드는 생성 버튼을 누를 때만 만든다.

다음은 앞선 제안을 반영한 **변경 가능한 구현 기본값**이다. 사용자 지정 30회·요일·버튼 조건과 혼동하지 않는다.

| 항목 | 구현 기본값 |
|---|---|
| 직원 차감 | 유효 결과 생성·서버 저장 성공 시 1회. 기존 결과 조회·입력 오류·확정 실패는 미차감 |
| 주간 범위 | 해당 주 월요일 00:00부터 일요일 버튼 접수 시각까지 |
| 주간 현장 범위 | 전체 현장, 직원 및 관리자 업무. 모든 관리자가 하나의 결과 공유 |
| 주간 생성 제한 | 조직 전체 주당 성공 결과 1개, 실패 재시도 허용 |
| 코칭 범위 | 선택 직원의 전체 현장, 요청 시각에서 30일 전부터 요청 시각 직전까지 |
| 코칭 생성 제한 | 조직 전체 직원별 한국 날짜당 성공 결과 1개, 관리자들이 공유 |
| 가이드 범위 | 선택 현장 최근 30일 상담 기록 + 관리자가 검토한 현장 안내자료 |
| 가이드 생성 제한 | 조직 전체 현장별 한국 날짜당 성공 결과 1개 |
| 요약·질문 입력 | 현재 본인 담당 고객의 이용 가능한 기록. 이전 담당자 기록도 포함 |
| 비용 목표 | 조직 전체 AI 모델 사용료 월 USD 5의 시작 설정. 공급자 청구의 절대 상한 보장은 아님 |
| 실행 동시성 | 계정당 처리 중 1개, 서버 전체 외부 호출 동시 실행 2개로 시작 |

기존 결과 읽기는 요일·생성 횟수 제한에 포함하지 않는다. 관리자 일일 제한에 도달하면 새 생성 대신 기존 결과를 연다. 완료 후 강제 재생성 버튼은 초기 범위에서 제공하지 않는다.

### 19.2 직원 AI 버튼 및 출력

오늘의 DB·나의 DB의 각 행에서 실행한다. 로그인·직원 역할·현재 담당·삭제 여부·비밀번호 변경 완료·한도·키 설정을 서버에서 검사한다.

| 기능 코드 | 버튼 | 출력 |
|---|---|---|
| CLEANUP | AI 상담 정리 | 정리한 메모 + 통화결과·방문예약·재콜·주택상황·계약여부 추천 |
| SUMMARY | 상담 요약 | 이전 상담 핵심, 관심·우려, 약속한 후속 조치, 이번 확인 사항 |
| NEXT_QUESTIONS | 다음 질문 제안 | 구체적인 다음 질문 3~5개와 각 질문의 목적·근거 |

- 버튼 클릭 시 해당 행의 편집을 확정하고 미저장 내용부터 일반 저장한다. 저장 실패·충돌이면 AI 요청하지 않고 횟수를 차감하지 않는다. 다른 행의 대기열은 기존 규칙을 유지한다.
- 모델 입력은 서버가 권한 확인 후 읽은 저장 데이터로 구성한다. 클라이언트가 임의 고객 기록·분석 대상·프롬프트를 보내지 못하게 한다.
- CLEANUP은 정리 메모와 추천 필드를 나란히 보여준다. 고객명·연락처·담당자·내부 필드·삭제 여부는 출력 schema의 변경 대상에서 제외한다.
- 근거 없는 항목은 `NO_SUGGESTION`으로 표시하여 기존 값을 유지한다. `null`을 자동 삭제 지시로 해석하지 않는다.
- 상대 날짜는 요청 기준 한국 날짜와 해당 원문 작성 시각을 함께 제공한다. 오래된 메모의 `내일`을 현재의 내일로 바꾸지 않는다. 날짜·시각이 불명확하면 추천 일시를 확정하지 않고 확인이 필요한 이유만 표시한다.
- 직원이 추천 필드를 체크하고 `선택 항목 적용`을 눌러야 편집 대기열에 반영한다. 기본은 미선택이다. 기존 notes를 교체하는 경우 원문·제안문을 비교하도록 하며 이전 원문은 ConsultationRevision에 남긴다.
- SUMMARY·NEXT_QUESTIONS는 읽기용이며 고객 notes를 자동 변경하지 않는다.
- 응답에는 사용한 고객 버전·할당 ID·생성 시각·근거 이력 ID를 포함한다. 생성 이후 고객 버전이 바뀌면 과거 결과임을 표시하고 자동 적용을 막는다. 직원은 최신 값과 비교해 일반 편집으로 반영할 수 있다.
- 제안이 적용된 시점에도 현재 할당·권한을 검증한다. 실제 저장 성공 때만 진행 기록을 생성한다.
- 생성·조회·적용 각각 서버 권한을 확인한다. 이전에 본인 담당이었던 고객의 결과도 회수 후에는 직원이 다시 조회할 수 없다.
- 결과를 본 뒤 적용하지 않아도 성공 생성 1회는 차감한다. 결과가 반환되어 서버에 저장됐으면 브라우저 응답 유실만으로 차감을 취소하지 않는다.

### 19.3 주간 업무 브리핑

- 서버 한국 요일이 일요일일 때만 **새 요청 접수** 가능하다. 월~토에는 생성 버튼을 비활성화하고 `일요일에 생성할 수 있습니다` 안내를 표시한다.
- 보고서 키는 ISO 주차 문자열만 사용하지 말고 `week_start_date(월요일 날짜)`를 unique로 사용한다. 연말 주차 경계도 정확히 처리한다.
- 접수 시 데이터 cutoff를 고정한다. 일요일 늦게 접수한 작업이 월요일에 끝나도 일요일 접수 시각까지의 결과다. 자동으로 다음 주 데이터를 섞지 않는다.
- 보고서 제목 아래 `분석 기간: 월요일 00:00 ~ 일요일 HH:mm / 일요일 업무는 집계 시각까지 포함`을 표시한다.
- 일요일 오전에 생성한 결과는 하루 종료 결과가 아니다. 주당 1회 기본값에 따라 기존 결과만 조회하므로 UI에 `이번 주 생성 1회 사용`을 안내한다.
- 근거가 있는 모든 현장·실제 처리자 정보를 포함한다. 비활성화되었더라도 분석 기간에 업무를 수행한 직원·관리자 이력은 누락하지 않는다.

필수 보고서 구성:

1. **직원 업무 현황:** 할당·현재 보유·진행, 기간 내 상담 변경 고객 수, 통화결과, 방문·계약 상태 변경, 재콜 완료·기한 경과. 통화 녹음/발신 로그가 없으므로 수정 횟수를 `실제 통화 횟수`라고 부르지 않는다.
2. **팀장 업무 현황:** 업로드·분배·회수·담당자 변경·삭제 요청 승인·대기. 기간 안의 담당 관리자와 작업 시각을 기준으로 집계한다.
3. **고객 반응·거절 사유:** 가격·위치·시기·비교 검토 등 근거가 확인되는 사유, 반복 질문, 사유 미기재. 복수 사유는 중복 집계임을 표시한다.
4. **상담 기록 검토 보조:** 재연락 언급과 일정 누락, 방문 취소와 예약 잔존, 상담내용과 통화결과 불일치 등. 날짜가 비어도 허용하는 기존 규칙을 유지하며 오류 강제 수정 대신 `확인 필요`로 제시한다.
5. **다음 주 확인할 업무:** 지연 재콜·미처리 요청 등 근거와 함께 제안. 자동 실행하지 않는다.

- 총수·비율·차이는 서버 SQL/도메인 집계로 계산한다. AI가 임의 숫자를 보완하지 못하도록 집계 값을 읽기 전용 참조로 제공한다.
- 메모 분류 결과는 source ID별 검증한 라벨로 저장하고 집계는 서버에서 수행한다. 같은 고객·기간에 겹치는 메모 버전은 별도 고객으로 세지 않는다.
- 사례에는 권한 확인된 내부 고객 링크를 붙인다. 모델이 임의 URL을 생성하지 않는다. 입력에 없는 source ID는 제거하고 근거 없음으로 표시한다.

### 19.4 직원별 30일 코칭

- 직원별 `AI 코칭` 버튼으로 실행한다. 요청 직전 30×24시간 구간을 기본으로 하고 시작·끝 시각을 표시한다.
- 현재 담당자 기준으로 과거 업무를 귀속시키지 않는다. ConsultationRevision.actor_id, Assignment, Callback 처리자·시각, OperationEvent를 기준으로 해당 직원의 실제 업무를 추출한다.
- 이전 코칭을 입력으로 제공한다. 토큰 절감을 위해 최근 코칭 최대 3개와 그 이전의 구조화된 실행 항목·미확인 과제를 포함하는 기본값을 둔다. 모든 과거 본문을 매번 무제한 전송하지 않는다.
- 출력: 확인되는 강점 / 반복 개선점 / 이전 코칭 대비 관찰된 변화 / 구체적인 질문·후속 조치 예시 / 다음 확인 항목.
- 이전 코칭 전후의 관찰 기간과 근거 수를 표시한다. 기간이 부족하거나 전후 비교 자료가 없으면 개선 여부를 `판단 불가`로 표시한다. 코칭이 변화의 원인이라고 단정하지 않는다.
- 최초 코칭이면 `이전 코칭 없음`을 표시한다. 실제 음성 없이 말투·태도·통화 품질·성격·직원 순위를 추측하지 않는다.
- 결과는 관리자만 조회한다. 직원에게 자동 전송하거나 별도 알림 메시지를 보내지 않는다.
- 코칭 원문과 구조화 실행 항목을 이력으로 저장하고 다음 분석의 참조 관계를 기록한다.

### 19.5 팀 공통 상담 가이드

- 선택 현장과 최근 30일 상담내용을 기준으로 관리자가 버튼을 눌러 초안을 생성한다.
- 현장 안내자료는 관리자가 직접 입력·검토하는 텍스트로 시작한다. 가격·계약조건·혜택·입주일 등은 이 자료에 근거가 있을 때만 답변 초안에 포함한다. 직원 메모를 공식 상품 조건의 근거로 승격하지 않는다.
- 안내자료가 없으면 일반 질문과 확인 순서만 생성하고 사실정보는 `현장 담당자 확인 필요`로 표시한다. 별도 웹 검색·파일 검색 유료 도구는 초기 범위에 추가하지 않는다.
- 구성: 상담 시작 질문 / 관심별 추가 질문 / 반복 질문 답변 초안 / 거절·보류 응대 예시 / 재콜·방문예약 확인 / 기록 작성 기준.
- 상태: DRAFT → 관리자 검토·수정 → PUBLISHED. 생성만으로 게시하지 않는다.
- 직원은 해당 현장의 게시된 버전만 조회한다. 새 초안이 생겨도 기존 게시본은 새 버전 게시 전까지 유지한다.
- 직접 수정·게시·기존 버전 조회는 AI를 호출하지 않으며 생성 횟수도 차감하지 않는다.
- 가이드에는 고객명·연락처·개별 고객 상세·직원 코칭 원문을 포함하지 않는다. 직원에게는 팀 공통 내용만 보여준다.

### 19.6 상담 이력과 신규 모델

**ConsultationRevision**

- 고객 ID·현재 할당 ID(nullable)·실제 작성자·서버 저장 시각·고객 버전·변경 필드·변경 전후 상담 값·notes 본문을 보관한다.
- 변경 출처: MANUAL / AI_APPLIED / IMPORT / BASELINE / SYSTEM_DELETE_NOTE. AI_APPLIED는 원본 AI 결과 ID도 참조한다.
- 실제 상담 값 변경과 이력 생성은 같은 트랜잭션이다. 일반 사용자에게 과거 이력 편집·삭제 API를 제공하지 않는다. 고객·현장 영구 삭제 시는 함께 제거한다.
- IMPORT·BASELINE·SYSTEM_DELETE_NOTE를 직원 상담 실적으로 세지 않는다. 가져온 메모의 원래 통화 시각을 알 수 없으면 알 수 없다고 표시한다.
- 기존 앱에 추가할 때 현존 notes를 BASELINE으로 1회 보관하고 도입 시각을 기록한다. 과거 작성일·작성자를 추측하지 않는다. 30일 기록이 아직 쌓이지 않았으면 확보된 기간만 분석한다.
- 같은 상담 메모의 100초 저장본들을 별도 통화로 계산하지 않는다. 서버는 고객·작성자·업무 날짜별 최신 유효 메모와 의미 있는 필드 변경을 묶고, 근거 원본 버전은 참조로 보존한다.

**AIRequest / AIResult**

- request: UUID, 요청자, 기능 코드, 고객·할당·직원·현장 대상, 접수 시각, 기준 한국 날짜, 기간 start/end, source fingerprint, prompt/schema/model 버전, idempotency key, 상태, provider request ID, 오류 코드.
- 상태: RESERVED / RUNNING / SUCCEEDED / FAILED / CANCELLED / UNKNOWN. 토큰·비용·시도별 기록은 성공 여부와 별도로 남긴다.
- result: 검증된 JSON 결과, 생성 시각, source 고객 버전·근거 이력 참조, 보고서 기준 키, 이전 코칭 참조, 가이드 상태·검토자·게시 시각.
- 요청은 서버측 모델·프롬프트만 사용한다. 클라이언트가 provider/model/key를 지정할 수 없다.
- 고객 결과는 요청 직원에게만 제공하되 현재 권한도 확인한다. 관리자 보고서는 관리자 공용, 코칭은 관리자 전용, 게시 가이드는 직원 공개 범위로 분리한다.

**AIQuotaBucket / AIUsageAttempt / AIReportSlot**

- QuotaBucket: `(user_id, korean_date)` unique, successful_count, reserved_count. 직원 한도는 합계 30 이하.
- UsageAttempt: 공급자별 실제 시도·입출력 토큰·추론 토큰 등 청구 단위·단가 버전·예상/확정 비용·통화(USD). 실패한 유료 시도도 보존한다.
- ReportSlot: `(feature, scope_key, period_key)` unique. 주간은 GLOBAL+월요일 날짜, 코칭은 직원 ID+한국 날짜, 가이드는 현장 ID+한국 날짜. 예약·성공 결과를 연결해 여러 관리자의 중복 생성을 막는다.

**SiteKnowledge / AIResultSource**

- SiteKnowledge: 현장·제목·본문·버전·검토 관리자·검토 시각·유효 여부. 현재 유효한 검토본만 상품 사실 근거로 사용한다.
- AIResultSource: 결과별 원본 고객·상담 이력·안내자료·이전 AI 결과를 참조한다. 원본 및 파생 결과 무효화에 사용한다.

### 19.7 호출·한도·캐시·재시도

1. 사용자가 버튼을 클릭한다. 서버가 인증·역할·현재 담당·요일·입력·AI 설정을 확인한다.
2. 같은 idempotency key 요청이 있으면 같은 작업 또는 결과를 반환한다. 본문이 다르면 충돌이다.
3. 사용 가능한 기존 동일 결과가 있으면 공급자를 호출하지 않고 반환한다. 캐시 키는 기능·사용자 권한 범위·할당 ID·데이터 버전·기준 날짜·분석 기간·프롬프트·모델 버전을 포함한다. 오래된 상대 날짜 결과를 무조건 재사용하지 않는다.
4. 짧은 디비 트랜잭션에서 계정의 일일 횟수 또는 관리자 ReportSlot과 조직 비용을 원자적으로 예약한다. 성공 29회+예약 1회면 추가 요청은 거부한다.
5. 트랜잭션을 종료한 뒤 서버가 외부 AI를 호출한다. 네트워크 응답을 기다리며 공통 advisory lock·고객 행 잠금을 유지하지 않는다.
6. 입력 fingerprint와 결과 schema·근거·현재 권한을 검증한다. 공급자 응답을 HTML/코드/SQL로 실행하지 않는다.
7. 유효한 결과를 저장하고 예약을 성공 횟수로 전환한다. 권한이 사라졌으면 결과 노출을 취소하고 예약을 해제한다. 공급자 비용이 발생했다면 비용 기록은 남긴다.
8. 실패가 확정되면 FAILED로 기록하고 예약을 해제한다. 직원이 동일 요청을 재조회해도 새 호출을 만들지 않는다. 새 실행은 명시적인 버튼 클릭으로만 시작한다.

- 접수일 기준 차감: 23:59 접수 후 다음 날 완료해도 접수일 한도를 사용한다.
- 전송됐는지 불명확한 timeout은 UNKNOWN으로 기록한다. 공급자 확인 기능이 있으면 확인하고, 없다면 원래 요청의 완료를 기다리는 상한 기간을 둔다. 사용자에게 미확인 상태를 알리고 유료 재호출을 자동 수행하지 않는다.
- 구현 기본값으로 10분 안에 결과를 확인할 수 없으면 실패로 종료하고 사용자 횟수 예약은 해제하되 비용은 보수적 예상치로 남긴다. 해당 요청은 종료된 뒤 늦은 응답이 와도 성공으로 바꾸거나 고객에게 적용하지 않는다.
- 확실히 전송 전 실패 또는 공급자가 요청 미수행을 명시한 일시 오류만 같은 논리 요청에서 최대 1회 재시도한다. schema 오류 교정을 위해 무제한 호출하지 않는다.
- 직원 30회는 사용자에게 보여주는 성공 사용 제한이다. 과금 시도 수와 같지 않으며 관리자 비용 화면에는 두 값을 구분한다.
- AI 요청 하나가 내부 분할 호출 여러 개를 필요로 해도 사용자 성공 횟수는 1회다. 모든 내부 호출 비용은 합산하고 제한한다.
- 기존 DB 기반 작업 큐와 같은 앱 이미지의 worker를 사용해 긴 보고서를 처리할 수 있다. 새 AI 작업을 만드는 주체는 버튼 요청뿐이다. worker가 이미 접수된 작업을 실행하는 것은 자동 생성이 아니다. worker는 앱 서버와 같은 VM에서 구동한다.
- 작업 상태 조회는 실행 중 화면에서만 제한적으로 수행하고 완료 시 중단한다. 상태 GET은 새 AI 호출·횟수 차감을 하지 않는다.

### 19.8 비용 최소화·분석 범위 제한

- 처음에는 외부 텍스트 API 공급자 하나, 검증한 저가 모델 하나를 사용한다. 모델 이름은 설정으로 받되 출시·중단·가격·한국어 결과 품질을 구현 시 공식 자료와 샘플로 확인한다. 특정 모델의 영구 제공·무료 운영을 보장하지 않는다.
- 웹 검색·음성 인식·이미지 처리·임베딩·벡터 디비·모델 학습은 초기 범위에서 제외한다.
- 가짜 데이터로 품질·quota·실패 테스트를 수행한다. 실제 API 호출 테스트는 키·모델·비용 설정 후 소량으로 수행하고 결과를 구분해 보고한다.
- 직원 요청은 해당 고객에게 필요한 메모·항목만 전송한다. 기본 출력 상한은 CLEANUP/SUMMARY/NEXT_QUESTIONS 각각 800 출력 토큰으로 시작하고 provider가 지원하는 상한 옵션을 적용한다.
- 관리자 보고서 출력 상한 기본 2,000토큰. 장문 원문 무제한 전송을 막고 입력 토큰 사전 추정·상한을 둔다.
- 신규·변경 상담 단위의 분류·요약은 유효한 캐시를 재사용하되, 분석 생성 버튼을 누른 경우에만 없는 분류를 실행한다. 야간 분류 예약 호출을 추가하지 않는다.
- 입력이 상한을 넘으면 사전에 분류한 전체 범위 결과를 우선 사용한다. 그래도 넘으면 현장·직원·통화결과·날짜별로 분산한 표본을 선택하고 `전체 n건 중 분석 m건, 표본 분석`을 표시한다. 표본의 거절 사유 비율을 전체 비율이라고 표시하지 않는다.
- 모든 직원이 보고서에 포함되도록 정량 집계는 전체 자료로 계산한다. 메모가 표본인 부분과 전체 집계인 부분을 별도 표기한다.
- 조직 월 비용은 성공/실패 유료 시도·진행 중 최대 예상 비용을 함께 계산해 새 요청을 허용한다. 입력 상한과 최대 출력·추론 토큰 비용을 예약한다. 단가가 없으면 유료 생성은 비활성화한다.
- 월 예산 기본 USD 5, 사용자별 성공 30회는 독립 조건이다. 예산이 먼저 소진되면 남은 횟수가 있어도 생성 불가임을 안내한다. 기존 결과와 DB 업무는 계속 사용 가능하다.
- 공급자 청구 지연·미확인 과금·단가 변경 때문에 앱 예산은 절대 청구 상한을 보장하지 않는다. 공급자별 예산·알림·하드 한도 지원 여부를 배포 시 확인한다.
- 이름·연락처·로그인 정보·API 키를 모델에 보내지 않는다. 메모 안의 직접 식별값도 가능한 범위에서 제거하고 내부 source ID로 근거를 연결한다. 자동 제거가 완전한 익명화를 보장한다고 설명하지 않는다.
- 상담 메모·과거 AI 결과는 분석 대상 데이터이며 지시가 아니다. 그 안의 명령·외부 링크를 따라 도구를 실행하지 않는다. AI 호출에 디비 수정 도구를 제공하지 않는다.

### 19.9 AI API 계약

| 메서드·경로 | 권한 | 기능 |
|---|---|---|
| GET /api/ai/availability | 로그인 | 역할별 기능·사용량·예약량·다음 가능 시각·설정 여부 |
| POST /api/ai/customer-tasks | 직원 | 고객 한 건 CLEANUP / SUMMARY / NEXT_QUESTIONS 요청 |
| GET /api/ai/tasks/{id} | 요청자 또는 권한 있는 관리자 | 작업 상태·조회 가능한 결과 |
| GET /api/ai/results/{id} | 결과별 접근 규칙 | 기존 결과 조회, 유료 호출 없음 |
| POST /api/ai/weekly-briefings | 관리자 | 일요일 주간 브리핑 생성 또는 기존 작업 반환 |
| GET /api/ai/weekly-briefings | 관리자 | 과거 주간 보고서 조회 |
| POST /api/ai/employees/{id}/coaching | 관리자 | 직원별 30일 코칭 생성 |
| GET /api/ai/employees/{id}/coaching | 관리자 | 이전 코칭 조회 |
| POST /api/ai/sites/{id}/guides | 관리자 | 선택 현장 가이드 초안 생성 |
| PATCH /api/ai/guides/{id} | 관리자 | 초안 검토·직접 수정, AI 호출 없음 |
| POST /api/ai/guides/{id}/publish | 관리자 | 초안 게시, AI 호출 없음 |
| GET /api/sites/{id}/published-guide | 로그인 | 게시된 해당 현장 가이드 조회 |
| GET /api/ai/usage | 관리자 | 기능별 횟수·예약·비용·실패 현황 |
| GET/POST /api/sites/{id}/knowledge | 관리자 | 현장 안내자료 조회·등록 |
| PATCH /api/sites/{id}/knowledge/{knowledge_id} | 관리자 | 자료 수정·검토본 지정 |

- 생성 POST는 idempotency key 필수. 직원 요청은 고객 ID·할당 ID·expected_version·기능만 받는다. API 키나 사용자 지정 system prompt를 받지 않는다.
- 신규 작업은 202와 task ID, 완료된 기존 결과는 200과 result ID를 반환한다. 직원 추천 적용은 기존 batch-update API를 사용하고 source_ai_result_id를 기록한다.
- 오류: AI_NOT_CONFIGURED / AI_DAILY_LIMIT / AI_BUDGET_LIMIT / AI_BUSY / AI_SUNDAY_ONLY / AI_SCOPE_LIMIT / AI_INPUT_TOO_LARGE / AI_PROVIDER_FAILED / AI_OUTCOME_UNKNOWN / AI_RESULT_STALE. 기존 인증·할당·삭제 오류도 유지한다.
- GET 상태·결과 API에도 현재 역할·담당자 검사를 적용한다. 불투명한 ID를 안다는 것만으로 접근할 수 없다.

### 19.10 기록 삭제·분석 이력의 일관성

- 고객을 휴지통에 옮기면 직원 AI 조회·생성은 차단한다. 관리자 과거 기간 분석에는 해당 기간 업무를 포함할 수 있지만 휴지통 상태를 명시한다.
- 고객·현장 영구 삭제 시 ConsultationRevision, 해당 고객의 직원 AI 결과, 캐시된 입력·분류·응답 원문을 삭제한다.
- 삭제 고객을 근거로 포함한 혼합 브리핑·코칭·가이드와 이를 다시 참조한 파생 결과는 AIResultSource 관계로 재귀 무효화하고 본문을 제거한다. 새 유료 생성은 자동 수행하지 않는다.
- 사용자에게 `원본 삭제로 결과를 더 이상 제공할 수 없습니다`를 표시한다. 게시 가이드가 영향을 받으면 게시를 해제한다.
- 원문 없는 사용 횟수·토큰·비용·생성 시각 메타데이터는 유지한다. 영구 삭제가 이미 쓴 일일 횟수나 비용을 되돌리지 않는다.
- 원본이 삭제된 과거 코칭은 다음 코칭 입력에서 제외한다. 여러 현장에 같은 연락처가 있다는 이유로 다른 현장의 원본을 삭제하지 않는다.

## 20. AI API 키 전용 파일·Git 제외

### 20.1 파일 역할

| 파일 | 내용 | Git 포함 |
|---|---|---|
| .env.ai | 실제 서버용 AI_API_KEY 및 공급자·모델·단가 설정 | 금지 |
| .env.ai.example | 항목 이름·빈 키·설명용 기본값 | 허용 |
| .env | 일반 앱의 비밀 환경 설정 | 금지 |
| .env.example | 일반 앱 설정 예시, 실제 비밀값 없음 | 허용 |
| .gitignore | 키 파일 및 환경 파일 제외 규칙 | 허용 |
| .dockerignore | 빌드 컨텍스트에서 키 파일 제외 | 허용 |

이 문서와 함께 제공하는 `.env.ai`는 **빈 API 키를 넣은 로컬 입력용 파일**이다. 사용자는 해당 파일의 AI_API_KEY 값에 키를 직접 입력한다. 채팅으로 키를 보내거나 소스코드에 붙여 넣지 않는다. 예시 파일은 키를 채우는 대상이 아니다.

```dotenv
AI_ENABLED=false
AI_PROVIDER=
AI_MODEL=
AI_API_KEY=
AI_MONTHLY_BUDGET_USD=5
AI_INPUT_USD_PER_MILLION=
AI_OUTPUT_USD_PER_MILLION=
```

- 구현 시 지원 공급자와 검증한 모델·단가를 설정한다. 추론 토큰 등 별도 과금이 있는 모델은 단가 설정·예산 계산에 반영한다.
- 직원 하루 30회·팀장 생성 주기 같은 업무 제한은 서버 코드/검증된 설정으로 관리하고 브라우저가 수정하지 못하게 한다.
- AI_ENABLED=true여도 키·모델·단가가 준비되지 않으면 AI 생성만 비활성화하고 `관리자 설정 필요`를 표시한다.
- `.env.ai` 로딩 자체는 프레임워크가 자동 보장하지 않는다. 설정 모듈에서 명시적으로 로딩하고 실제 프로세스 환경변수 우선, 파일은 누락값 보완으로 정의한다.
- Docker Compose에서는 서버 web·AI worker에만 런타임 env_file로 전달한다. 프런트엔드 빌드·프록시·PostgreSQL·일반 회수 scheduler에는 키를 전달하지 않는다.
- 코드 저장소에서 다른 위치에 배포한다면 AI_ENV_FILE 경로를 지정할 수 있게 한다. 서버별 파일을 따로 관리하고 컨테이너 이미지에 COPY하지 않는다.
- Unix 환경에서 `.env.ai`는 소유자만 읽고 쓰도록 0600 권한을 적용한다. 환경 출력·디버그 화면·오류 응답에서 실제 키를 노출하지 않는다.

### 20.2 .gitignore 필수 규칙

```gitignore
# Local environment files and credentials
.env
.env.*
!.env.example
!.env.ai.example
secrets/
```

- 실제 키는 `.env.ai.example`에도 절대 넣지 않는다.
- 기존 `.gitignore`가 있으면 기존 규칙을 보존하고 병합한다.
- `.gitignore`는 이미 추적 중인 파일이나 과거 커밋에서 키를 제거하지 않는다. 구현 시 먼저 추적 여부를 확인한다.
- 이미 추적된 실제 키 파일은 작업 파일을 유지한 채 인덱스에서 제외하는 조치를 검토하고, 이미 커밋·외부 전송된 키는 폐기·재발급한다. 이력 재작성은 별도 영향 검토 없이 수행하지 않는다.
- 같은 제외 규칙을 `.dockerignore`에도 적용해 업로드된 빌드 컨텍스트·이미지 레이어에 키가 들어가지 않게 한다. 추가로 `.git`·로컬 캐시·백업 파일을 제외한다.

### 20.3 구현 완료 확인

1. `git check-ignore -v -- .env.ai`에서 제외 규칙을 확인한다. 값이 아닌 파일 이름만 검사한다.
2. `git ls-files --error-unmatch -- .env.ai`가 추적 파일을 찾지 못해야 한다.
3. `.env.ai.example`은 추적 가능한 상태이고 AI_API_KEY가 비어 있어야 한다.
4. 커밋 예정 변경·로그·테스트 fixture·클라이언트 번들에 실제 키가 없는지 검사한다. 검사 결과에 키 원문을 출력하지 않는다.
5. 실제 저장소가 없는 설계서 폴더에서는 임시 Git 저장소로 ignore 규칙만 검증할 수 있다. 이것을 실제 운영 저장소의 커밋 이력 검사 완료라고 보고하지 않는다.
6. 문서를 다른 프로젝트에 전달할 때는 설계서·`.env.ai.example`·ignore 규칙을 전달한다. 실제 `.env.ai`는 전달·push하지 않고 대상 환경에서 빈 예시로 새로 만든다.

## 22. 최종 적용 원칙

사용자가 확정한 고객명·연락처 수정 금지, 공통 초기 비밀번호, 직원당 분배 수량, 오늘 할당 전체의 수동 회수, 수정 이력 기준의 오늘 23시 자동 회수, 상담정보 유지, 100초 이내 배치 전송, 복사·우클릭 제한, 직원 행별 삭제 요청과 관리자 승인 후 비고 기록·휴지통 이동을 임의로 다른 권장사항으로 교체하지 않는다.

직원 AI 세 기능의 버튼 실행·하루 총 30회 제한, 팀장의 일요일 주간 브리핑·직원별 지난 30일과 이전 코칭 분석·버튼 기반 팀 가이드, API 키 별도 파일과 Git 제외도 동일하게 준수한다. AI 공급자나 문장 생성 편의를 위해 기존 권한·수정 금지·진행 판정·삭제 승인 규칙을 우회하지 않는다.

구현 중 이 문서 안에서 충돌이 발견되면 조용히 추정하지 말고 해당 조항과 영향 범위를 제시한다. 구현 기본값 수준의 변경은 이유와 검증 결과를 기록하되, 승인된 업무 규칙의 변경이 필요하면 사용자에게 확인한다.
